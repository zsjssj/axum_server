# 05 请求生命周期与路由

**本章目标**：把一个 HTTP 请求从进入进程到离开进程的每一步拆开看清楚。学完你应该能回答："这个请求先经过谁？""Handler 参数为什么这个顺序？""为什么校验错误能返回 422 而不是 Axum 的默认纯文本？"

---

## 5.1 Axum 的四个核心概念

| 概念 | 是什么 | 本项目位置 |
| --- | --- | --- |
| `Router` | 路由表：路径 + 方法 → 处理函数 | `src/app/routes.rs` |
| `Handler` | 处理函数：提取参数 → 返回响应 | `src/modules/*/handler.rs` |
| `Extractor` | 提取器：把请求的某部分变成 Rust 值 | `src/common/extractor.rs` |
| `Layer` / 中间件 | 包在 Handler 外面的处理环节 | `src/common/auth.rs`、`src/app/middleware.rs` |

关键是理解 `Handler` 的签名不是随便写的，**参数顺序在类型系统里是有约束的**：

```rust
// src/modules/user/handler.rs:53
pub(crate) async fn create_user(
    State(state): State<AppState>,                     // ← FromRequestParts
    _current_user: CurrentUser,                        // ← FromRequestParts
    ValidatedJson(req): ValidatedJson<CreateUserRequest>,  // ← FromRequest，吃掉请求体
) -> Result<impl IntoResponse, AppError>
```

Axum 对 Handler 参数的规则：

1. **除最后一个外，所有参数都必须实现 `FromRequestParts`**——它们只用请求的"可分离部分"（头、路径、查询串、扩展）。
2. **最多一个参数实现 `FromRequest`**——它会**消费**请求体，所以必须放在最后。
3. **返回值必须实现 `IntoResponse`**；返回 `Result<T, E>` 时 `E` 必须实现 `IntoResponse`。

第 3 条是项目能用 `?` 的关键：`AppError` 实现了 `IntoResponse`（`src/common/error.rs:83`），所以 Handler 里任何 `?` 都能直接变成 422/409/500 响应。

> **常见编译错误**：把 `ValidatedJson` 放在 `State` 前面。报错信息是"trait bound `String: FromRequestParts` not satisfied"之类，看着很绕，但原因就是**请求体只能被消费一次，所以消费它的参数必须最后**。

## 5.2 路由表：三组路由，三种保护级别

```rust
// src/app/routes.rs:22
pub fn create_app(...) -> Router {
    Router::new()
        .merge(routes::health_routes())      // 第 1 组：匿名
        .merge(routes::api_routes(state.clone()))  // 第 2 组：默认要登录
        .merge(openapi::routes())            // 第 3 组：匿名（文档）
```

### 第 1 组：运维探针，必须匿名

```rust
// src/app/routes.rs:17
pub fn health_routes() -> Router<AppState> {
    Router::new()
        .route("/", get(root_handler))
        .route("/health", get(health_handler))
        .route("/ready", get(readiness_handler))
}
```

如果健康检查也需要登录，编排系统的探针永远拿不到 200，会把所有实例判为不健康然后全部重启——一次配置失误直接导致全网故障。

### 第 2 组：业务接口，默认拒绝

```rust
// src/app/routes.rs:33
pub fn api_routes(state: AppState) -> Router<AppState> {
    let api = Router::new()
        .route("/hello", get(hello_handler))
        .merge(auth::routes())
        .merge(user::routes())
        // 用 `route_layer` 而不是 `layer`
        .route_layer(axum::middleware::from_fn_with_state(state, crate::common::auth::require_login));

    Router::new().nest("/api/v1", api)
}
```

这里有三个非常值得学的设计，逐一拆解。

#### `nest("/api/v1", api)`：前缀剥离

`nest` 会把 `/api/v1` 从路径上**剥掉**再交给内部 Router。所以：

| 客户端请求 | 内部 Router 看到的路径 |
| --- | --- |
| `GET /api/v1/users` | `/users` |
| `POST /api/v1/auth/login` | `/auth/login` |

这解释了为什么 `src/modules/auth/handler.rs:33` 里注册的是 `LOGIN_PATH`（值为 `/auth/login`，见 `src/common/auth.rs:40`）而不是完整路径。

`nest` 的另一个效果：内部路由自动获得前缀，新增模块不用重复写 `/api/v1`。

#### `route_layer` 而不是 `layer`

这是**行为差异**，不是风格差异：

| 用法 | 作用范围 | 未注册路径的表现 |
| --- | --- | --- |
| `.layer(mw)` | 该 Router 上的**所有**请求，包括没匹配到路由的 | `GET /api/v1/not-exists` 未登录 → **401** |
| `.route_layer(mw)` | 只作用于**已匹配到路由**的请求 | `GET /api/v1/not-exists` → **404** |

项目选了 `route_layer`，因为"不存在的接口没必要先要求登录"。这个行为还有集成测试锁定（`src/app/mod.rs:279` 的 `returns_not_found_for_unknown_api_route`）。

#### 认证挂在**路由组**上，不挂在 Handler 上

对比两种写法：

```rust
// 写法 A（本项目）：默认全组拒绝，白名单放行
.route_layer(from_fn_with_state(state, require_login))

// 写法 B（反面）：每个 Handler 声明需要认证
.route("/users", get(list_users))       // ← 靠人记得加认证
```

写法 B 的失效方向是**不安全的**：新人加一个接口忘声明认证，就是一个匿名可访问的接口，只有 code review 能发现。写法 A 的失效方向是**安全的**：忘做什么都不会暴露，因为默认就是拒绝。唯一的"例外清单"集中在 `common::auth` 的 `PUBLIC_PATHS` 里（见[第 08 章](./08-全局状态与中间件.md)）。

### 第 3 组：文档

```rust
// src/app/openapi.rs:73
pub fn routes() -> Router<AppState> {
    Router::new()
        .merge(SwaggerUi::new("/swagger-ui").url("/api-docs/openapi.json", ApiDoc::openapi()))
}
```

Swagger UI 本身要公开可访问，否则没法看文档。它是静态页面，不含业务数据。

## 5.3 一个请求的完整流水线

以 `POST /api/v1/users` 为例，从外到内：

```text
① TCP 连接（带 ConnectInfo，为审计准备客户端 IP）
        ↓
② 日志层 TraceLayer  （app/mod.rs:33）——最后挂，所以最外层；进入时记 span，返回时记耗时
        ↓
③ CORS 层            （app/mod.rs:31）
        ↓
④ 路由匹配：/api/v1/** → nest 剥离前缀 → 内部路径 /users
        ↓
⑤ 认证中间件 require_login（app/routes.rs:40）
     白名单命中？→ 放行
     否则：读 access_token Cookie → 验签 → 查 Redis 吊销 → 写入 AuthUser 扩展
     任一步失败 → 401（在进入 Handler 之前）
        ↓
⑥ Handler 参数解析（按声明顺序逐个提取）
     State<AppState>              ← 从 Router 状态克隆
     CurrentUser                  ← 从请求扩展读取
     ValidatedJson<CreateUserRequest> ← 反序列化 + validator 校验
        ↓
⑦ Service：生成 public_id、spawn_blocking 算 Argon2、调用 Repository
        ↓
⑧ Repository：参数化 INSERT ... RETURNING
        ↓
⑨ 原路返回：Handler 包 ApiResponse → 201
        ↓
⑩ 日志层记录状态码与耗时
```

注意第 ⑤ 步的位置：认证失败**不会进入 Handler**，所以 Handler 不需要写 `if !logged_in`。这就是"横切能力放在中间件"的价值。

## 5.4 提取器：把"解析 + 校验 + 错误转换"打包

裸写 Axum 会遇到一个问题：`Json<CreateUserRequest>` 提取失败时返回的是 Axum 自己的纯文本/JSON 错误，形状和项目的 `ApiResponse` 不一致。项目的解法是包一层自定义提取器。

### ValidatedJson

```rust
// src/common/extractor.rs:15
pub struct ValidatedJson<T>(pub T);

#[async_trait]
impl<S, T> FromRequest<S> for ValidatedJson<T>
where
    S: Send + Sync,
    T: DeserializeOwned + Validate,     // 约束：必须可反序列化且可校验
{
    type Rejection = AppError;          // 关键：拒绝类型就是项目错误类型

    async fn from_request(request: Request, state: &S) -> Result<Self, Self::Rejection> {
        let Json(value) = Json::<T>::from_request(request, state)
            .await
            .map_err(json_rejection_to_error)?;   // 解析错误 → AppError
        value.validate()?;                        // 校验错误 → From<ValidationErrors> → AppError
        Ok(Self(value))
    }
}
```

三个设计点：

1. **`type Rejection = AppError`**。Axum 要求拒绝类型实现 `IntoResponse`；因为 `AppError` 实现了，所以提取失败自动变成统一信封的错误响应。
2. **复用 Axum 的 `Json` 提取器**再加工，而不是自己读 body 解析。这样 `Content-Type` 检查、body 大小限制、`BytesRejection` 这些细节都不用重写。
3. **`value.validate()?` 用的是 `Validation(#[from] ValidationErrors)`**（`src/common/error.rs:41`，`#[from]` 展开为 `impl From<ValidationErrors> for AppError`），所以校验失败自动走 422 + 字段明细。

### 解析错误怎么映射

```rust
// src/common/extractor.rs:77
fn json_rejection_to_error(rejection: JsonRejection) -> AppError {
    match rejection {
        JsonRejection::MissingJsonContentType(_) =>
            AppError::UnsupportedMediaType("Content-Type 必须为 application/json"),
        JsonRejection::JsonDataError(_) =>
            AppError::UnprocessableEntity("JSON 请求字段不合法"),
        JsonRejection::JsonSyntaxError(_) =>
            AppError::BadRequest("JSON 请求体语法错误"),
        JsonRejection::BytesRejection(_) =>
            AppError::BadRequest("读取请求体失败"),
        _ => AppError::BadRequest("JSON 请求体格式错误"),
    }
}
```

| 客户端问题 | 变体 | HTTP | 业务码 |
| --- | --- | --- | --- |
| 忘了 `Content-Type: application/json` | `UnsupportedMediaType` | 415 | 40002 |
| JSON 结构对但字段类型/缺字段/多字段 | `UnprocessableEntity` | 422 | 40001 |
| JSON 语法错误（比如 `{`） | `BadRequest` | 400 | 40000 |
| body 读不出来（连接中断） | `BadRequest` | 400 | 40000 |

这个映射表的意义：**同是"客户端发错了"，也要让调用方分得清是格式问题还是语义问题**。把 415 混成 400 会让前端排查很久。

### ValidatedQuery 与 ApiPath

```rust
// src/common/extractor.rs:35  查询参数
let Query(value) = Query::<T>::from_request_parts(parts, state)
    .await
    .map_err(|_| AppError::BadRequest("查询参数格式错误"))?;
value.validate()?;
```

```rust
// src/common/extractor.rs:55  路径参数
pub struct ApiPath<T>(pub T);

impl<S, T> FromRequestParts<S> for ApiPath<T> where T: FromStr + Send, T::Err: Debug {
    async fn from_request_parts(parts: &mut Parts, state: &S) -> Result<Self, Self::Rejection> {
        let Path(raw_value) = Path::<String>::from_request_parts(parts, state)
            .await
            .map_err(|_| AppError::BadRequest("路径参数缺失"))?;
        let value = raw_value.parse::<T>()
            .map_err(|_| AppError::BadRequest("路径参数格式错误"))?;
        Ok(Self(value))
    }
}
```

`ApiPath` 多绕了一步：先取 `String`，再 `parse::<T>()`。为什么不直接 `Path::<Uuid>`？因为 Axum 自己的拒绝响应是纯文本，绕过了信封。**所有面向客户端的入口都必须能产出统一错误形状**，这是本项目贯穿始终的约束。

于是 Handler 里路径参数也是统一写法：

```rust
// src/modules/user/handler.rs:110
pub(crate) async fn get_user(
    State(state): State<AppState>,
    _current_user: CurrentUser,
    ApiPath(public_id): ApiPath<Uuid>,
) -> Result<impl IntoResponse, AppError>
```

注意 `ApiPath<Uuid>` 这类参数是 `FromRequestParts`，所以可以出现在 body 提取器之前。

### 路由里的路径语法

```rust
// src/modules/user/handler.rs:31
.route("/users/:public_id", get(get_user).put(update_user).delete(delete_user))
```

Axum 0.7 用 `:name` 表示路径参数（0.8 改成了 `{name}`）。**OpenAPI 注解里必须写 `{public_id}` 这种花括号形式**（`src/modules/user/handler.rs:101`），两者语法不同，别混。

## 5.5 Handler 的三条职责边界

Handler 只做三件事，多一件都是越界：

```rust
// src/modules/user/handler.rs:53
pub(crate) async fn create_user(
    State(state): State<AppState>,        // ① 拿到依赖
    _current_user: CurrentUser,           // ① 声明"需要登录"
    ValidatedJson(req): ValidatedJson<CreateUserRequest>,  // ① 拿到已校验的参数
) -> Result<impl IntoResponse, AppError> {
    let user = UserService::create_user(&state.db, req).await?;   // ② 调用业务

    Ok((StatusCode::CREATED, Json(ApiResponse::success("用户创建成功", user))))  // ③ 组装响应
}
```

| 该做 | 不该做 |
| --- | --- |
| 提取参数、调用 Service、包装响应 | 写 SQL |
| 决定成功时的 HTTP 状态码（201/200） | 决定"用户名重复该返回什么"（那是 Service 的事） |
| 从 `AppState` 取依赖传给 Service | 直接访问 `env::var`、全局单例 |

注意 `_current_user` 前缀下划线：这个 Handler 不需要用户身份，但**故意保留参数**，因为它是"该接口需要登录"的显式声明。虽然真正拦截的是中间件，但签名让读代码的人一眼看出这个接口的访问要求。

## 5.6 动手练习

1. **加一个回声接口**：注册 `POST /api/v1/echo`，接收 `{"message": String}` 并返回它。要求：用 `ValidatedJson`（给它一个 `length(max = 100)` 规则），失败时返回 422。写完用 curl 测两种失败：超长、语法错误。
2. **验证参数顺序**：把 `create_user` 的 `ValidatedJson` 挪到 `State` 前面，记录编译错误原文，然后还原。这个错误信息以后你会遇到很多次，值得记住长相。
3. **验证 route_layer 语义**：临时把 `api_routes` 里的 `route_layer` 改成 `layer`，然后不带 Cookie 访问 `/api/v1/not-exists`，观察从 404 变成 401。**改完还原。**
4. **加一个只有路径参数的接口**：`GET /api/v1/users/{public_id}/exists`，不用 `ApiPath` 而直接 `Path<Uuid>`，然后请求一个非 UUID 的路径，对比响应形状和用 `ApiPath` 时的差别。
5. **看完整调用链**：在 `create_user` 的 Handler、Service、Repository 各加一行 `tracing::info!`，请求一次，观察日志顺序。
