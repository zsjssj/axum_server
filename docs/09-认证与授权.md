# 09 认证与授权

**本章目标**：完整拆解本项目的认证体系。这是全仓库代码量最大、安全约束最密集的部分，也是最值得反复读的一章。学完你应该能独立回答："为什么用两个令牌？""为什么登出后 access token 立刻失效？""为什么用户名不存在也要算一次 Argon2？"

> **先分清两个词**：**认证（Authentication）**是"你是谁"，**授权（Authorization）**是"你能做什么"。本项目只做了认证 + 一个粗糙的设计——登录即可访问全部业务接口，没有角色与权限模型。这是刻意的简省，扩展方向见[第 14 章](./14-生产化与进阶.md)。

---

## 9.1 方案总览

```text
                     ┌─────────────────────────────────────────┐
   POST /auth/login  │ 校验凭证 → 签发两个令牌 → 都用 Set-Cookie 下发 │
                     └─────────────────────────────────────────┘
                                    │
              ┌─────────────────────┴─────────────────────┐
              ▼                                           ▼
   access_token (JWT, HS256)                  refresh_token (256 位随机值)
   · 15 分钟                                  · 7 天
   · 无状态，服务端不存                        · 数据库只存 SHA-256 摘要
   · 放 Cookie，HttpOnly                      · 放 Cookie，HttpOnly
   · 登出时把 jti 写进 Redis 吊销列表            · 落库会话，可即时吊销
              │                                           │
              ▼                                           ▼
   每个 /api/v1 请求由中间件校验              POST /auth/refresh 换取新令牌对
   （验签 + 查吊销）                          （轮换：旧的立刻作废）
```

| 令牌 | 格式 | 有效期 | 服务端状态 | 能否单独吊销 |
| --- | --- | --- | --- | --- |
| access token | JWT（HS256） | 15 分钟 | 无状态（可选 Redis 吊销记录） | 只能靠 Redis 吊销列表 |
| refresh token | 256 位随机值 | 7 天 | `user_sessions` 表存摘要 | 数据库标记 `revoked_at` |

**为什么不用一个长期 JWT？** 因为 JWT 无状态，签发后在过期前无法收回。要么有效期很长（泄露后长期可用），要么很短（用户频繁重新登录）。双令牌把这对矛盾拆开：短期的 access token 承担"每次请求的校验"，长期的 refresh token 承担"续期"，并且 refresh token 有服务端状态、可以随时吊销。

## 9.2 access token：JWT 的每个字段都在做一件事

```rust
// src/modules/auth/service.rs:46
struct AccessClaims {
    sub: String,   // 用户内部主键（i64 转字符串）
    iss: String,   // 签发者
    exp: i64,      // 过期时间（Unix 秒）
    iat: i64,      // 签发时间
    jti: String,   // 令牌唯一标识 —— 吊销列表的键
    typ: String,   // "access"，防止 refresh 冒充
}
```

逐字段设计意图：

| 字段 | 取值来源 | 作用 |
| --- | --- | --- |
| `sub` | `user_id.to_string()` | 受保护接口直接按主键加载用户，命中主键索引；**不放 `public_id`**，省掉一次"公开 ID → 内部 ID"的转换查询 |
| `iss` | `jwt.issuer` | 多服务共用密钥时区分签发者，校验时断言 |
| `exp` | 当前时间 + `access_ttl_minutes` | 短有效期是泄露窗口的上限 |
| `iat` | 当前时间 | 排查与审计 |
| `jti` | `{public_id}:{毫秒时间戳}` | 吊销的键；用毫秒保证同一用户同秒多次登录也不同 |
| `typ` | `"access"` | **必需的安全约束**，见下 |

### 算法必须写死 HS256

```rust
// src/modules/auth/service.rs:442
let mut validation = Validation::new(Algorithm::HS256);   // 显式指定，绝不从令牌头部读
validation.set_issuer(&[jwt_config.issuer.as_str()]);
validation.set_required_spec_claims(&["exp", "iss", "sub"]);
validation.validate_aud = false;
validation.leeway = 5;                                     // 允许 5 秒时钟偏移
```

**绝不从令牌头部读取 `alg`**。为什么：

| 攻击 | 原理 |
| --- | --- |
| `alg = none` | 令牌头部声明"不签名"，实现如果信任头部就跳过验签 → 可伪造任意用户 |
| 算法混淆 | 服务端用 RSA 公钥验签时，攻击者把算法改成 HS256，**用公钥当 HMAC 密钥**签名 → 验签通过 |

这两种攻击在历史上都真实发生过（jwt 库的 CVE）。防御只有一条：**服务端决定算法，客户端无权协商。**

`leeway = 5` 是多实例部署的实用取舍：不同机器的时钟可能差一两秒，没有 leeway 会让刚签发的令牌在某些实例上被判过期。

### `typ` 断言：挡掉"令牌混用"

```rust
// src/modules/auth/service.rs:464
if token_data.claims.typ != TOKEN_TYPE_ACCESS {
    return Err(AppError::Unauthorized("认证令牌类型错误"));
}
```

如果少了这一行会怎样？refresh token 是随机值不是 JWT，看起来无法冒充。但**一旦将来有人把 refresh token 也改成 JWT**（比如为了加"设备信息"而改成 JWT），这个检查就失效了——长效令牌就能当短期令牌用，整个"短有效期"设计被绕过。

测试锁定了这个行为：

```rust
// src/modules/auth/service.rs:624
fn rejects_token_with_wrong_type() { /* 构造 typ = "refresh" 的合法签名令牌，断言被拒 */ }
```

### 过期与无效要分开报

```rust
// src/modules/auth/service.rs:454
.map_err(|error| match error.kind() {
    jsonwebtoken::errors::ErrorKind::ExpiredSignature => AppError::Unauthorized("认证令牌已过期"),
    other => {
        tracing::debug!(?other, "access token 校验失败");
        AppError::Unauthorized("认证令牌无效")
    }
})?
```

客户端据此决定行为：**"已过期" → 去调 `/auth/refresh`；"无效" → 直接跳登录页**。如果两者统一成一句话，客户端只能一律重新登录，体验差且刷新机制形同虚设。注意两种文案都不泄露签名细节。

### 签发

```rust
// src/modules/auth/service.rs:410
fn encode_access_token(jwt_config: &JwtConfig, user_id: i64, public_id: Uuid, now: DateTime<Utc>)
    -> Result<String, AppError>
{
    let claims = AccessClaims {
        sub: user_id.to_string(),
        iss: jwt_config.issuer.clone(),
        exp: (now + ChronoDuration::minutes(jwt_config.access_ttl_minutes)).timestamp(),
        iat: now.timestamp(),
        jti: format!("{public_id}:{}", now.timestamp_millis()),
        typ: TOKEN_TYPE_ACCESS.to_owned(),
    };

    encode(&Header::new(Algorithm::HS256), &claims,
           &EncodingKey::from_secret(jwt_config.secret.as_bytes()))
    .map_err(|error| {
        tracing::error!(%error, "access token 签发失败");
        AppError::Internal("令牌签发失败")
    })
}
```

注意 `now` 是**参数**而不是在函数里调 `Utc::now()`。这让签发逻辑可测试——测试可以传一个确定的时间点。同理 `AccessClaims` 的构造集中在一个函数里，签发与校验共用同一个结构体，字段增删不会两边不同步。

## 9.3 refresh token：随机值为什么比 JWT 好

```rust
// src/modules/auth/service.rs:473
fn generate_refresh_token() -> String {
    let mut bytes = [0u8; REFRESH_TOKEN_BYTES];   // 32 字节 = 256 位
    rand::thread_rng().fill_bytes(&mut bytes);
    to_hex(&bytes)                                 // 64 位十六进制字符串
}
```

```rust
// src/modules/auth/service.rs:486
/// 使用 SHA-256 而不是 Argon2：刷新令牌本身已是 256 位随机值，不存在
/// 字典攻击空间；摘要的作用是防止数据库泄露后令牌被直接复用，
/// 而 Argon2 的慢速特性会在每次刷新时带来不必要的延迟。
fn hash_token(token: &str) -> String {
    let digest = Sha256::digest(token.as_bytes());
    to_hex(&digest)
}
```

三个设计决定，每个都值得推敲：

**① 为什么不用 JWT？** refresh token 只需要"不可猜测"，不需要被解析。而"可解析"恰恰带来"无状态"——无状态就意味着**无法即时吊销**。用随机值 + 数据库存储，反而让吊销变成一次 `UPDATE`。

**② 为什么哈希用 SHA-256 而不是 Argon2？** 密码用 Argon2 是因为密码熵低（人有习惯，可字典攻击）。32 字节随机值有 2²⁵⁶ 种可能，暴力枚举无意义，所以**不需要慢哈希**。用 Argon2 只会让每次刷新多几十毫秒。

**③ 为什么存摘要而不是原文？** 数据库泄露时，攻击者拿到摘要也反推不出原文（SHA-256 单向 + 高熵输入）。这和"密码不存明文"是同一个道理。

> **对比记忆**：慢哈希保护"低熵秘密"（密码），快哈希保护"高熵秘密"（令牌）。用错方向就是浪费性能或留下爆破空间。

## 9.4 登录流程：12 步，每一步都有原因

```rust
// src/modules/auth/service.rs:77
pub async fn login(db, redis, jwt_config, auth_config, username, password, context)
    -> Result<TokenPair, AppError>
```

| 步骤 | 代码 | 为什么 |
| --- | --- | --- |
| 1 | `:86` 取当前时间与窗口 | 计算滑动窗口起点 |
| 2 | `:93` **先查限流** | 见下方"顺序"说明 |
| 3 | `:95` 超阈值 → 429 | 即使密码正确也拒绝（限流语义如此） |
| 4 | `:100` 按用户名查凭证 | 走 `idx_users_username` |
| 5 | `:104` 用户不存在 → 执行 dummy 哈希 | 抹平响应时间差 |
| 6 | `:106` 记录失败（数据库 + Redis） | 审计与计数 |
| 7 | `:107` 返回统一凭证错误 | 与密码错误文案一致 |
| 8 | `:112` Argon2 校验（阻塞线程池） | CPU 密集 |
| 9 | `:114` 密码错 → 记录失败 + 统一错误 | 同上 |
| 10 | `:126` 清理窗口外的历史审计 | 防表无限增长 |
| 11 | `:128` 签发令牌对 + 落库会话 | 见 `issue_token_pair` |
| 12 | Handler 下发两个 Cookie | 见 9.5 |

### 顺序：为什么必须先限流再校验密码

```rust
// src/modules/auth/service.rs:90
// 先判定限流，再执行密码校验。顺序不能颠倒：Argon2 校验被刻意设计得很慢，
// 若先校验密码，大量失败请求会持续占用阻塞线程池，使限流本身变成
// 消耗服务端算力的攻击面。
```

量化一下：Argon2 一次约 30–100ms，`spawn_blocking` 线程池默认上限是 512 个任务、但真正跑在工作线程上的数量有限。如果先算密码，攻击者每秒发 1000 个错误请求就能让阻塞线程池排队到超时，**正常用户的登录也会被拖死**。先做一次轻量的 Redis/DB 计数查询，就能在消耗算力之前把攻击挡掉。

### 时间攻击与用户枚举

```rust
// src/modules/auth/service.rs:104
let Some(credentials) = credentials else {
    let _ = verify_password_dummy(password).await;      // 照常算一次 Argon2
    Self::record_login_failure(db, redis, username, context.client_ip, window).await?;
    return Err(invalid_credentials());
};
```

如果用户不存在就立刻返回，响应时间会明显短于"用户存在但密码错"。攻击者用几万次请求统计耗时，就能枚举出哪些用户名真实存在——这是后续撞库的起点。

防御是**让两条路径耗时对齐**：

```rust
// src/modules/auth/service.rs:527
async fn verify_password_dummy(password: &str) -> Result<(), AppError> {
    tokio::task::spawn_blocking(move || {
        // 对比一个固定的合法哈希，校验结果本身没有意义，只取其计算耗时
        let _ = verify_password_blocking(&password, DUMMY_PASSWORD_HASH);
    }).await.map_err(|_| AppError::Internal("密码校验任务失败"))?;
    Ok(())
}
```

注意 `DUMMY_PASSWORD_HASH` 必须是**格式合法的 Argon2 输出**：

```rust
// src/modules/auth/service.rs:544
const DUMMY_PASSWORD_HASH: &str = "$argon2id$v=19$m=19456,t=2,p=1$AAAAAAAAAAAAAAAAAAAAAA$AAAA...";
```

如果它无法被解析，`verify_password_blocking` 会在计算开始前就失败返回，"不存在"分支反而更快——防护彻底失效。所以有一个专门的测试守着它：

```rust
// src/modules/auth/service.rs:778
fn dummy_password_hash_is_parseable() { assert!(PasswordHash::new(DUMMY_PASSWORD_HASH).is_ok()); }
```

> 这个测试是整个项目里最"反直觉但最有价值"的测试之一：**它守护的不是功能，而是一个安全前提。**

### 失败文案必须完全一致

```rust
// src/modules/auth/service.rs:397
fn invalid_credentials() -> AppError {
    AppError::Unauthorized("用户名或密码错误")
}
```

"用户不存在"和"密码错误"返回**同一个** 401 + 同一句话。任何差异（文案、状态码、响应头、耗时）都是枚举通道。

### 失败计数：Redis 是判定层，数据库是审计层

```rust
// src/modules/auth/service.rs:144
async fn count_login_failures(db, redis, username, window, window_start) -> Result<i64, AppError> {
    match redis.login_failure_count(username, window).await {
        Ok(count) => Ok(count),
        Err(error) => {
            tracing::warn!(%error, %username, "Redis 登录失败计数不可用，回退到数据库统计");
            Ok(AuthRepository::count_failures_since(db, username, window_start).await?)
        }
    }
}
```

这就是"降级策略写在 Service"的又一例：计数读 Redis（快、自动过期、多实例共享），失败时回退数据库（慢但准确）。限流**不会静默失效**。

```rust
// src/modules/auth/service.rs:164
async fn record_login_failure(db, redis, username, client_ip, window) -> Result<(), AppError> {
    AuthRepository::record_failure(db, username, client_ip).await?;   // 先写审计

    if let Err(error) = redis.record_login_failure(username, window).await {
        tracing::warn!(%error, %username, "Redis 登录失败计数写入失败，后续判定将回退到数据库统计");
    }
    Ok(())
}
```

写数据库失败会向上传播（审计丢了不行）；写 Redis 失败只告警（判定会自动回退）。**两种失败的不同处理，体现了"哪一个是权威"的判断。**

### 登录成功后为什么不清空计数

```rust
// src/modules/auth/service.rs:119
// 注意这里只清理数据库中的过期审计记录，不清空 Redis 中的窗口内计数：
// 成功登录不能证明之前的失败不是攻击行为，清空计数等于给攻击者一个
// 「只要偶尔成功一次就能重置限额」的入口。
AuthRepository::clear_failures_before(db, username, window_start).await?;
```

如果成功就清零，攻击者的策略变成"每猜 4 次密码，用已知正确的账号成功登录一次"，限额永远重置不了。这是个很细但很真实的设计。

### 窗口最小值兜底

```rust
// src/modules/auth/service.rs:405
fn rate_limit_window(auth_config: &AuthConfig) -> Duration {
    Duration::from_secs((auth_config.login_window_minutes * 60).max(60) as u64)
}
```

配置校验已经拒绝非正数，这里再 `max(60)` 是**防线内兜底**。为什么值得多写这一行？因为"窗口为 0"意味着所有失败记录立刻过期 = 限流被关闭，而且不会有任何报错。多一层保证比事后排查便宜得多。

## 9.5 刷新与轮换：重放检测

```rust
// src/modules/auth/service.rs:187
pub async fn refresh(db, jwt_config, refresh_token, client_ip, user_agent) -> Result<TokenPair, AppError> {
    let token_hash = hash_token(refresh_token);
    let session = AuthRepository::find_session_with_user(db, &token_hash).await?
        .ok_or_else(|| AppError::Unauthorized("刷新令牌无效"))?;

    // ① 重放检测
    if session.is_revoked {
        tracing::warn!(user_id = session.user_id, "检测到已吊销的刷新令牌被再次使用，强制该用户全部会话下线");
        AuthRepository::revoke_all_sessions_for_user(db, session.user_id).await?;
        return Err(AppError::Unauthorized("刷新令牌已失效，请重新登录"));
    }

    // ② 过期判定
    if session.expires_at <= Utc::now() {
        return Err(AppError::Unauthorized("刷新令牌已过期，请重新登录"));
    }

    // ③ 签发新令牌对（新会话已落库）
    let token_pair = Self::issue_token_pair(db, jwt_config, session.user_id, session.public_id, client_ip, user_agent).await?;

    // ④ 旧会话标记吊销并记录轮换关系
    let new_session_id = AuthRepository::find_session_with_user(db, &hash_token(&token_pair.refresh_token)).await?
        .ok_or(AppError::Internal("令牌会话写入后无法读取"))?.id;
    AuthRepository::rotate_session(db, session.id, new_session_id).await?;

    Ok(token_pair)
}
```

### 重放检测在防什么

```text
正常流程：
  客户端用 RT1 刷新 → 服务端发 RT2，RT1 标记已吊销
  客户端下次用 RT2 → 正常

令牌泄露场景：
  攻击者偷到 RT1；合法客户端也用它刷新了一次 → RT1 被吊销
  攻击者再用 RT1 → 命中 is_revoked = true → 判定泄露 → 该用户全部会话下线
```

**代价是合法用户也被踢下线**（无法分辨谁是攻击者）。这是刻意选择：宁可多一次登录，也不允许已泄露的令牌继续可用。响应文案也说明了原因："刷新令牌已失效，请重新登录"。

### 这带来一条客户端硬约束

> **不要并发发起多个刷新请求。**

并发刷新的后果：两个请求都带 RT1，一个成功（RT1 吊销、发 RT2），另一个命中重放检测 → **该用户所有设备全部下线**。这类"服务端正确、客户端踩坑"的设计必须在 API 文档里写清楚（[reference/AUTH_API.md](./reference/AUTH_API.md) 有专节说明）。

### 顺序：为什么先落新会话，再吊销旧会话

```rust
// 新会话已经落库（issue_token_pair 内部完成）
// 才把旧会话标记吊销 + 写 replaced_by
```

反过来先吊销旧会话，如果签发新令牌失败，用户就处于"旧令牌失效、新令牌没拿到"的状态 —— 只能重新登录。当前顺序下最坏情况是"多了一条未使用的会话记录"，无害。

## 9.6 登出：幂等 + 两类凭据

```rust
// src/modules/auth/handler.rs:256
pub(crate) async fn logout(State(state): State<AppState>, headers: HeaderMap) -> Result<impl IntoResponse, AppError> {
    if let Some(refresh_token) = cookie::refresh_token_from_headers(&headers, &state.auth.cookie)
        && let Err(error) = AuthService::logout(&state.db, &refresh_token).await
    {
        tracing::warn!(?error, "登出时吊销会话失败，仍继续清除客户端 Cookie");
    }

    if let Some(access_token) = cookie::access_token_from_headers(&headers, &state.auth.cookie)
        && let Err(error) = AuthService::revoke_access_token(&state.redis, &state.jwt, &access_token).await
    {
        tracing::warn!(?error, "登出时写入 access token 吊销列表失败，令牌将在自然过期前继续有效");
    }

    cleared_session_response(&state.auth.cookie, "登出成功")
}
```

三个设计点：

**① 两边都是"尽力而为"。** 任一吊销失败都只告警、继续清 Cookie。理由：让客户端卡在"无法退出"的状态，比一次吊销失败更糟。

**② 用 `if let ... && let Err(...)` 的 let-chains。** 这是 Rust 2024 edition 的新语法（项目 `edition = "2024"`），相当于 `if let Some(x) = ... { if let Err(e) = ... { } }` 的扁平写法。

**③ 幂等。** 没有令牌、令牌无效、会话不存在，一律返回成功：

```rust
// src/modules/auth/service.rs:240
pub async fn logout(db: &PgPool, refresh_token: &str) -> Result<(), AppError> {
    let token_hash = hash_token(refresh_token);
    let Some(session) = AuthRepository::find_session_by_token_hash(db, &token_hash).await? else {
        // 令牌无法对应任何会话，说明它从未被签发或已被清理。
        // 从调用方视角登出目标已达成，因此同样返回成功而不是报错。
        return Ok(());
    };
    AuthRepository::revoke_session(db, session.id).await?;
    Ok(())
}
```

### access token 的立即吊销

```rust
// src/modules/auth/service.rs:264
pub async fn revoke_access_token(redis: &RedisStore, jwt_config: &JwtConfig, token: &str) -> Result<(), AppError> {
    let Ok(claims) = decode_access_claims(jwt_config, token) else {
        return Ok(());       // 解析不了：本来就通不过认证，不用吊销
    };

    let remaining = claims.exp - Utc::now().timestamp();
    if remaining <= 0 {
        return Ok(());       // 已过期：同上
    }

    redis.revoke_access_token(&claims.jti, Duration::from_secs(remaining as u64)).await
        .map_err(|error| { tracing::warn!(%error, "写入 access token 吊销列表失败"); AppError::Internal("令牌吊销失败") })
}
```

**TTL = 令牌剩余有效期**，而不是固定值。令牌自然过期后吊销记录就没意义了，让它一起消失可以避免键无限累积。这两条"直接返回成功"的短路也很重要：写入一条永远不会被查询的记录只是浪费内存。

## 9.7 Cookie：安全属性逐个说

```rust
// src/common/cookie.rs:48
pub fn build_token_cookie(config: &CookieConfig, name: &str, value: &str, max_age_seconds: i64) -> String {
    Cookie::build((name.to_owned(), value.to_owned()))
        .path(config.path.clone())
        .http_only(true)                        // 固定启用，不可配置
        .secure(config.secure)                  // 生产必须 true
        .same_site(same_site(config))           // Strict 兜底
        .max_age(cookie::time::Duration::seconds(max_age_seconds))
        .build()
        .to_string()
}
```

| 属性 | 本项目取值 | 作用 |
| --- | --- | --- |
| `HttpOnly` | **固定 `true`** | 页面脚本无法读取令牌，XSS 只能"代为发请求"，无法窃取凭据长期冒用 |
| `Secure` | 配置控制（生产必须 `true`） | 只在 HTTPS 下发送 |
| `SameSite` | `Strict`（默认）/ `Lax` | 跨站请求不携带，防 CSRF 主防线 |
| `Path` | 配置，默认 `/` | 限制发送范围 |
| `Domain` | **刻意不设** | 省略时浏览器按"仅当前主机"处理，避免发到同父域的其他子域 |
| `Max-Age` | 各自匹配令牌有效期 | access 900 秒、refresh 604800 秒 |

**为什么不设 `Domain`？** 设成 `.example.com` 会让令牌发送给 `blog.example.com`、`api.example.com` 等所有子域；任何一个子域被攻破，令牌就泄露了。不设则只有当前主机能收到——更小的攻击面。

### 两个 Cookie 的有效期必须各自匹配

```rust
// src/modules/auth/handler.rs:81
// 两个 Cookie 的 Max-Age 必须各自匹配其令牌有效期，不能共用：
// 若 access token 的 Cookie 沿用刷新令牌的有效期，它会在令牌实际失效后
// 仍被浏览器持续发送，让服务端反复处理注定失败的请求。
append_set_cookie(&mut headers, build_token_cookie(cookie_config, &cookie_config.access_name, &tokens.access_token, tokens.expires_in))?;
append_set_cookie(&mut headers, build_token_cookie(cookie_config, &cookie_config.refresh_name, &tokens.refresh_token, refresh_ttl_seconds))?;
```

### 清除 Cookie 的属性必须完全一致

```rust
// src/common/cookie.rs:68
pub fn build_clear_cookie(config: &CookieConfig, name: &str) -> String {
    Cookie::build((name.to_owned(), String::new()))
        .path(config.path.clone())
        .http_only(true)
        .secure(config.secure)
        .same_site(same_site(config))
        .max_age(cookie::time::Duration::seconds(0))      // 立即过期
        // ...
}
```

浏览器按 **名称 + 域 + 路径** 匹配 Cookie。属性不一致（比如下发时 `Path=/`、清除时 `Path=/api`）会导致清除失败，令牌残留在客户端——用户以为登出了，实际还能用。测试锁定了这条：

```rust
// src/common/cookie.rs:218
fn clear_cookie_matches_issued_attributes() { /* 断言 Max-Age=0、HttpOnly、SameSite、Path 一致 */ }
```

### 为什么只接收 Cookie，不接收 `Authorization` 头

两个原因：

1. **旁路**：如果两种方式都支持，攻击者/客户端可以用 `Authorization` 绕开 `HttpOnly`、`SameSite` 这些只为 Cookie 设计的保护。
2. **一致性**：只保留一条认证路径，不存在"某条路径漏校验 Cookie"的差异化实现空间。

### 解析：多个同名 Cookie 怎么办

```rust
// src/common/cookie.rs:17
fn cookie_value(headers: &HeaderMap, name: &str) -> Option<String> {
    for header_value in headers.get_all(axum::http::header::COOKIE) {
        let Ok(raw) = header_value.to_str() else { continue; };   // 单个头非法就跳过
        for cookie in cookie::Cookie::split_parse(raw.to_owned()).flatten() {
            if cookie.name() == name { return Some(cookie.value().to_owned()); }
        }
    }
    None
}
```

注意两点：**遍历所有 `Cookie` 头**（浏览器可能拆成多个头），**遇到非法头继续而不是整体失败**（其他 Cookie 里可能还有有效令牌）。

## 9.8 CSRF：三层防御

Cookie 会自动随请求发送，这是它的便利也是它的风险。

| 层 | 措施 | 作用 |
| --- | --- | --- |
| 1（主） | `SameSite=Strict` | 跨站请求完全不携带令牌 Cookie |
| 2 | 写操作全部 `POST` + 强制 `application/json` | 浏览器对 `application/json` 的跨源请求会先发预检（`OPTIONS`），而 CORS 不会放行未授权来源 |
| 3 | 没有"用 GET 改状态"的接口 | 顶层 GET 导航不受 SameSite=Strict 保护，但当前没有副作用 |

放宽到 `Lax` 的残余风险要明确：外部站点的顶层 GET 导航会带 Cookie。当前所有写操作都是 POST，所以不影响认证状态——**但这是"当前恰好成立"，不是永远成立**。将来若加了 `GET /auth/logout` 这类接口，Lax 就有风险了。

## 9.10 生产环境必须做的三件事

| 事项 | 不做会怎样 |
| --- | --- |
| 替换 `APP__JWT__SECRET` | 配置文件里是公开的占位值；使用它等于任何人都能伪造任意用户令牌。长度校验能拒短密钥，但**识别不了已泄露的长密钥** |
| `APP__AUTH__COOKIE__SECURE=true` | 令牌在明文 HTTP 中传输，可被中间人截获 |
| 各实例 `jwt.secret` 一致 | 令牌在实例间随机失效，表现为用户"时好时坏地掉登录" |

以及：引导账号创建完成后关闭 `bootstrap.enabled` 并从部署环境移除凭据。

## 9.11 动手练习

1. **解码自己的令牌**：登录后从 `cookies.txt` 取 `access_token`，用 `jwt.io` 或本地脚本解码，对照 `AccessClaims` 逐字段确认。
2. **验证吊销**：登录 → 登出 → 用同一个 `access_token` 访问 `/auth/me`，期望 401 `认证令牌已失效，请重新登录`。然后停掉 Redis 再做一次，期望**仍然通过**（降级为"到期才失效"）。
3. **触发重放检测**：登录保存 RT1，用 `-b/-c` 刷新得到 RT2，然后**手工用 RT1 再刷新一次**，观察该用户全部会话被吊销。
4. **制造时间攻击对照组**：写一个小脚本，分别用"不存在的用户名"和"存在但密码错"各请求 50 次，记录平均耗时。两者应在同一量级（差异主要来自网络抖动）。
5. **加一条安全断言**：给 `decode_access_claims` 加一个 `aud`（受众）声明并校验，写出对应测试。思考：多服务共用密钥时，`aud` 比 `iss` 多解决什么问题？
