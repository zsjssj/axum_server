# 09 认证与授权

**本章目标**：完整拆解本项目的认证体系。这是全仓库安全约束最密集的部分，也是最值得反复读的一章。学完你应该能独立回答："为什么最终只签一个令牌？""为什么登出后令牌立刻失效？""为什么用户名不存在也要算一次 Argon2？"

> **先分清两个词**：**认证（Authentication）**是"你是谁"，**授权（Authorization）**是"你能做什么"。本项目只做了认证 + 一个粗糙的设计——登录即可访问全部业务接口，没有角色与权限模型。这是刻意的简省，扩展方向见[第 14 章](./14-生产化与进阶.md)。

---

## 9.1 方案总览

```text
                     ┌───────────────────────────────────────────┐
   POST /auth/login  │ 校验凭证 → 签发唯一登录令牌 → Set-Cookie 下发 │
                     └───────────────────────────────────────────┘
                                     │
                                     ▼
                     登录令牌 access_token（JWT, HS256）
                     · 有效期 7 天（jwt.ttl_minutes = 10080）
                     · 无状态：服务端不保存令牌本身
                     · HttpOnly Cookie 下发，页面脚本读不到
                     · 落一条审计记录（只存 SHA-256 摘要）
                                     │
                                     ▼
                     每个 /api/v1 请求由中间件校验
                     （验签 + 查 Redis 吊销列表）
                                     │
                                     ▼
                     过期 → 401「认证令牌已过期，请重新登录」
                     没有刷新入口，客户端只能重新登录
```

| 令牌 | 格式 | 有效期 | 服务端状态 | 能否单独吊销 |
| --- | --- | --- | --- | --- |
| 登录令牌 | JWT（HS256） | 7 天（`jwt.ttl_minutes`，默认 `10080` 分钟） | 无状态；`user_sessions` 只做审计，Redis 记吊销 | 只能靠 Redis 吊销列表，否则等自然过期 |

**注意一个容易误解的地方**：`user_sessions` 表里确实有 `token_hash`、`expires_at`、`revoked_at` 这些看起来像"会话状态"的列，但它在单令牌方案下**不参与每次请求的认证**。每次请求只做两件事：校验签名与 claims、查 Redis 吊销列表。这张表回答的是审计问题——"谁在什么时候、从哪个客户端登录过，什么时候登出"。

## 9.2 为什么本项目最终采用单令牌

单令牌不是"省事"，而是一次有明确代价的取舍。要讲清楚它，得先讲清楚双令牌本来在解决什么。

### 双令牌解决的问题

> 下面这段是**对照**，不是本项目的现状：本项目最终只签一个令牌。把双令牌复盘清楚，才能看懂后面的取舍依据。

JWT 无状态，签发之后在过期前无法收回。于是有效期的取值变成一对矛盾：

```text
有效期长 → 用户少登录，但令牌泄露后可被使用很久
有效期短 → 泄露窗口小，但用户频繁被踢回登录页
```

双令牌把这对矛盾拆成两个令牌：短期的 **access token**（如 15 分钟）承担"每次请求的校验"，长期的 **refresh token**（如 7 天，服务端有状态、可吊销）承担"续期"。access token 过期后，客户端用 refresh token 静默换一个新的——用户几乎永远不用重新登录，而泄露出去的 access token 只有 15 分钟可用。

这个设计在公网产品里是主流答案。但它不是免费的。

### 它带来的复杂度

| 复杂度 | 具体表现 |
| --- | --- |
| 两套 Cookie | 下发、清除、属性必须各自一致；两个名字还必须不相同（同名会互相覆盖，登录后刷新令牌直接丢失） |
| 刷新接口要匿名 | `/auth/refresh` 必须进白名单，否则 access token 一过期客户端就连"续期"这一步都进不去；白名单因此多一个匿名面 |
| 轮换策略 | 每次刷新签发新 refresh token 并把旧的标记吊销，还要记录 `replaced_by` 的轮换关系；顺序写反会出现"旧令牌失效、新令牌没拿到"的黑洞 |
| 重放检测 | 已吊销的 refresh token 被再次使用时，服务端无法分辨是攻击者还是合法客户端，只能吊销该用户全部会话 |
| 客户端硬约束 | 不能并发刷新——两个并发请求都带旧令牌，一个成功、一个命中重放检测，用户会被全部设备踢下线 |
| 会话表成为认证状态 | 刷新要读写数据库，多实例下这部分并发压力直接压到 PostgreSQL |

每一项单独看都是合理的，合起来就是：**为了"用户不用重新登录"，系统里多了一套凭据、一个匿名接口、一套轮换与检测逻辑，以及一条必须写进 API 文档的客户端约束。**

### 本项目的取舍

本项目最后选择的是：**7 天单令牌 + 过期重新登录 + Redis 吊销保证登出即时失效**。

| 维度 | 双令牌 | 单令牌（本项目） |
| --- | --- | --- |
| 令牌数量 / Cookie 数量 | 2 / 2 | **1 / 1** |
| 匿名白名单 | 3 项（含 `/auth/refresh`） | **2 项**（`/auth/login`、`/auth/logout`） |
| 服务端状态 | refresh 会话参与认证，需轮换 + 重放检测 | 会话表只审计；吊销列表放 Redis |
| 用户登录频次 | 只要 7 天内用过就永不登录 | **每 7 天登录一次** |
| 泄露窗口 | access 15 分钟（refresh 被滥用时更久，取决于检测） | **最长 7 天** |
| 登出即时失效 | refresh 可吊销，access 靠 Redis | **靠 Redis 吊销列表** |
| 客户端约束 | 不能并发刷新 | 无 |

为什么 7 天的窗口在本项目里可以接受？因为这是一个内部管理型服务：没有公开注册、没有多端长驻场景、敏感操作少，登录态泄露的后果主要是资料被读取。对应地，把有效期从 15 分钟拉长到 7 天带来的最大风险——泄露令牌长期可用——被两件事部分抵消：令牌只在 `HttpOnly` + `SameSite=Strict` 的 Cookie 里（XSS 拿不到、CSRF 带不出去），以及登出时立即写入 Redis 吊销列表。

### 残余风险必须写明

取舍不是"没有代价"，只是"代价已知"：

1. **令牌泄露后最长可用 7 天。** 服务端没有办法在自然过期前识别一个"合法签发但已泄露"的令牌，除非它被显式吊销。
2. **缓解手段有限。** 实际能做的只有三条：缩短 `jwt.ttl_minutes`（牺牲登录频次）、改密后强制该用户重新登录（当前项目未实现"改密即吊销历史令牌"）、人工把可疑令牌的 `jti` 写入吊销列表（当前没有管理接口）。
3. **Redis 故障时退化为"到期才失效"。** 吊销列表是 Redis 中的数据，查不到时按"未吊销"放行（见[第 08 章](./08-全局状态与中间件.md)与[第 10 章](./10-Redis与降级设计.md)）。

**什么时候应该换回双令牌？** 面向公网、有多端长驻会话、或存在需要"敏感操作前再认证"的场景时，双令牌（或短期 access + 服务端 session）的复杂度是值得付的。判断标准不是"哪种更先进"，而是**泄露窗口和登录频次，哪一个对本项目伤害更大**。

## 9.3 登录令牌：JWT 的每个字段都在做一件事

```rust
// src/modules/auth/service.rs:45
struct AccessClaims {
    sub: String,   // 用户内部主键（i64 转字符串）
    iss: String,   // 签发者
    exp: i64,      // 过期时间（Unix 秒）
    iat: i64,      // 签发时间
    jti: String,   // 令牌唯一标识 —— 吊销列表的键
    typ: String,   // "access"：令牌用途，写进契约
}
```

逐字段设计意图：

| 字段 | 取值来源 | 作用 |
| --- | --- | --- |
| `sub` | `user_id.to_string()` | 受保护接口直接按主键加载用户，命中主键索引；**不放 `public_id`**，省掉一次"公开 ID → 内部 ID"的转换查询 |
| `iss` | `jwt.issuer` | 多服务共用密钥时区分签发者，校验时断言 |
| `exp` | 当前时间 + `ttl_minutes` | 有效期是泄露窗口的上限；单令牌方案下它同时决定"一次登录能用多久" |
| `iat` | 当前时间 | 排查与审计 |
| `jti` | `{public_id}:{UUIDv7}` | 吊销的键；前缀便于日志定位用户，UUIDv7 保证同一毫秒内两次签发也不会重号（会话表以令牌摘要为唯一键，重号会撞唯一约束） |
| `typ` | `"access"` | 令牌用途的契约，见下 |

### 算法必须写死 HS256

```rust
// src/modules/auth/service.rs:319
let mut validation = Validation::new(Algorithm::HS256);   // 显式指定，绝不从令牌头部读
validation.set_issuer(&[jwt_config.issuer.as_str()]);
validation.set_required_spec_claims(&["exp", "iss", "sub"]);
validation.validate_aud = false;
validation.leeway = 5;                                     // 允许 5 秒时钟偏移
```

**绝不从令牌头部读取 `alg`**。为什么：

| 攻击 | 原理 |
| --- | --- |
| `alg = none` | 令牌头部声明"不签名"，实现如果信任头部就跳过验签 → 可伪造任意用户 |
| 算法混淆 | 服务端用 RSA 公钥验签时，攻击者把算法改成 HS256，**用公钥当 HMAC 密钥**签名 → 验签通过 |

这两种攻击在历史上都真实发生过（jwt 库的 CVE）。防御只有一条：**服务端决定算法，客户端无权协商。**

`leeway = 5` 是多实例部署的实用取舍：不同机器的时钟可能差一两秒，没有 leeway 会让刚签发的令牌在某些实例上被判过期。

### `typ` 断言：把"令牌用途"写进契约

```rust
// src/modules/auth/service.rs:340
if token_data.claims.typ != TOKEN_TYPE_ACCESS {
    return Err(AppError::Unauthorized("认证令牌类型错误"));
}
```

现在全系统只签发一种令牌，这项检查看起来纯属多余——确实没有别的令牌能拿来冒充。**但它防的不是今天，而是明天**：一旦将来引入其他用途的令牌（例如一次性登录链接、服务间调用令牌、密码重置令牌），忘记加这条断言就意味着那些令牌可以直接当登录凭据用。代码里那句注释说得很直白："今天只有一个令牌种类，这项检查看似多余，但它把「令牌用途」写进了契约。"

这类检查的价值在于**失败方向**：漏判的后果是越权使用，而多做一次比较的代价接近于零。

测试锁定了这个行为：

```rust
// src/modules/auth/service.rs:511
fn rejects_token_with_wrong_type() { /* 构造 typ = "other-purpose" 的合法签名令牌，断言被拒 */ }
```

### 过期与无效仍然分开报

```rust
// src/modules/auth/service.rs:332
.map_err(|error| match error.kind() {
    // 单令牌方案下「过期」不是可以自动续期的中间状态，客户端唯一的后续
    // 动作就是重新登录，因此文案只陈述事实，不暗示存在刷新接口。
    jsonwebtoken::errors::ErrorKind::ExpiredSignature => AppError::Unauthorized("认证令牌已过期，请重新登录"),
    other => {
        tracing::debug!(?other, "登录令牌校验失败");
        AppError::Unauthorized("认证令牌无效")
    }
})?
```

双令牌方案里，"已过期"意味着"去调刷新接口"，和"无效"（必须重新登录）是完全不同的客户端动作。单令牌方案下两者最终都指向登录页，**但文案仍然分开**，原因有三个：

1. **提示语气不同**：过期是正常生命周期，可以提示"登录已过期，请重新登录"；无效（签名错、被篡改、`iss` 不匹配）更像异常，客户端该清掉本地状态并打点上报。
2. **排障必须能区分**：日志里"大量过期"意味着 `ttl_minutes` 配得太短或客户端时钟异常；"大量无效"则可能是密钥不一致（多实例部署常见）或有人在伪造令牌。
3. **文案不泄露内部细节**：两句话都只陈述对客户端有用的结论，不暴露签名算法、`iss` 取值这类信息。

注意过期文案里写的是"请重新登录"而不是"请刷新"，因为**本项目没有刷新接口**——文案本身就在承诺系统的能力边界。

### 签发

```rust
// src/modules/auth/service.rs:298
fn encode_access_token(jwt_config: &JwtConfig, user_id: i64, public_id: Uuid, now: DateTime<Utc>)
    -> Result<String, AppError>
{
    let claims = AccessClaims {
        sub: user_id.to_string(),
        iss: jwt_config.issuer.clone(),
        exp: (now + ChronoDuration::minutes(jwt_config.ttl_minutes)).timestamp(),
        iat: now.timestamp(),
        jti: format!("{public_id}:{}", Uuid::now_v7()),
        typ: TOKEN_TYPE_ACCESS.to_owned(),
    };

    encode(&Header::new(Algorithm::HS256), &claims,
           &EncodingKey::from_secret(jwt_config.secret.as_bytes()))
    .map_err(|error| {
        tracing::error!(%error, "登录令牌签发失败");
        AppError::Internal("令牌签发失败")
    })
}
```

注意 `now` 是**参数**而不是在函数里调 `Utc::now()`。这让签发逻辑可测试——测试可以传一个确定的时间点。同理 `AccessClaims` 的构造集中在一个函数里，签发与校验共用同一个结构体，字段增删不会两边不同步。

有效期直接读 `jwt_config.ttl_minutes`，没有第二个"另一个令牌的有效期"可写错。`src/modules/auth/service.rs:432` 的测试 `token_expiry_follows_configured_ttl` 断言的正是"`exp - iat` 必须等于配置值"——单令牌方案下写死一个有效期，改配置就变成了无效操作。

## 9.4 会话审计：数据库里为什么只存摘要

登录时会同时写一条 `user_sessions` 记录，但它**不参与认证**，只回答审计问题。这不影响它的设计仍然值得推敲。

```rust
// src/modules/auth/service.rs:259
/// 生成登录令牌并写入一条会话审计记录。
async fn issue_token(db, jwt_config, user_id, public_id, client_ip, user_agent)
    -> Result<IssuedToken, AppError>
{
    let now = Utc::now();
    let ttl = ChronoDuration::minutes(jwt_config.ttl_minutes);

    let token = encode_access_token(jwt_config, user_id, public_id, now)?;

    // 只把摘要写入数据库：即使数据库泄露，攻击者也无法用摘要反推出
    // 可用于认证的原始令牌。这条记录仅用于审计，不参与每次请求的认证判定。
    let token_hash = hash_token(&token);
    AuthRepository::create_session(db, user_id, &token_hash, now + ttl, client_ip, user_agent).await?;

    Ok(IssuedToken::new(token, ttl.num_seconds()))
}
```

```rust
// src/modules/auth/service.rs:352
/// 计算令牌摘要。
///
/// 使用 SHA-256 而不是 Argon2：令牌本身是服务端签发的 JWT，不需要抵抗字典
/// 攻击（伪造者没有签名密钥就无法构造出可接受的令牌）；摘要的作用只是让
/// 数据库泄露时无法直接拿到可用令牌，而 Argon2 的慢速特性会在每次登录时
/// 带来不必要的延迟。
fn hash_token(token: &str) -> String {
    let digest = Sha256::digest(token.as_bytes());
    to_hex(&digest)
}
```

三个设计决定，每个都值得推敲：

**① 为什么存摘要而不是令牌原文？** 数据库泄露时，攻击者拿到摘要也反推不出原文（SHA-256 单向 + 高熵输入）。这和"密码不存明文"是同一个道理：**凭据可以验证，但不能还原**。

**② 为什么哈希用 SHA-256 而不是 Argon2？** 密码用 Argon2 是因为密码熵低（人有习惯，可字典攻击）。登录令牌是服务端用 HS256 签发的 JWT，攻击者没有密钥就构造不出可接受的令牌，不存在"猜"的空间，所以**不需要慢哈希**。而摘要要在每次登录时算一次，用 Argon2 只会白白多花几十毫秒。

**③ 为什么这张表只做审计、不参与每次请求的认证？** 如果每个请求都拿摘要去查库，JWT"无状态、不需要数据库往返"的收益就没了，多实例部署时这部分查询还会直接压到 PostgreSQL 上。所以单令牌方案里"令牌是否仍有效"只由两件事决定：**签名与 claims 校验** + **Redis 吊销列表**。会话表承担的是另一类问题——谁在什么时候、从哪个客户端登录过，什么时候登出。

> **对比记忆**：慢哈希保护"低熵秘密"（密码），快哈希保护"高熵秘密"（令牌）。用错方向就是浪费性能或留下爆破空间。

这条记录和令牌必须一次写成：先落库再签发，签发失败会留下指向不存在令牌的记录；先签发再落库，落库失败却把令牌给了客户端，审计与凭据就脱节了。所以 `issue_token` 的顺序固定为「签发 → 写摘要 → 返回」。

### 顺手清理的历史包袱

两个细节说明"改设计"往往还要处理残留：

- `user_sessions.replaced_by` 列是双令牌时代记录轮换链的，单令牌方案下没有轮换，它已经废弃。但**已经发布过的迁移不回头改**，所以新迁移 `migrations/004_document_single_token_sessions.sql` 只加 `COMMENT` 说明它已废弃，不改结构——修改已执行的迁移会让不同环境的库结构悄悄分叉。
- `rand` 依赖原先只为生成 256 位随机 refresh token 而存在，改为单令牌后它已从 `Cargo.toml` 移除。少一个依赖就少一条供应链与审计面，这类"设计简化带来的连带宽减"值得留意。

## 9.5 登录流程：12 步，每一步都有原因

```rust

pub async fn login(db, redis, jwt_config, auth_config, username, password, context)

```

| 步骤 | 代码 | 为什么 |
| --- | --- | --- |
| 1 | `:86`–`:88` 取当前时间与窗口起点 | 计算滑动窗口 |
| 2 | `:92` **先查限流** | 见下方"顺序"说明 |
| 3 | `:93` 超阈值 → 429 | 即使密码正确也拒绝（限流语义如此） |

| 5 | `:100` 用户不存在 → 执行 dummy 哈希 | 抹平响应时间差 |
| 6 | `:102` 记录失败（数据库 + Redis） | 审计与计数 |
| 7 | `:103` 返回统一凭证错误 | 与密码错误文案一致 |
| 8 | `:107` Argon2 校验（阻塞线程池） | CPU 密集 |
| 9 | `:108` 密码错 → 记录失败 + 统一错误 | 同上 |
| 10 | `:119` 清理窗口外的历史审计 | 防表无限增长 |
| 11 | `:120` 签发唯一令牌 + 写审计摘要 | 见 `issue_token`（9.4） |
| 12 | Handler 下发**一个** Cookie | 见 9.7 |

### 顺序：为什么必须先限流再校验密码

```rust
// src/modules/auth/service.rs:90
// 先判定限流，再执行密码校验。顺序不能颠倒：Argon2 校验被刻意设计得很慢，
// 若先校验密码，大量失败请求会持续占用阻塞线程池，使限流本身变成
// 消耗服务端算力的攻击面。
```

量化一下：Argon2 一次约 30–100ms，`spawn_blocking` 线程池默认上限是 512 个任务、但真正跑在工作线程上的数量有限。如果先算密码，攻击者每秒发 1000 个错误请求就能让阻塞线程池排队到超时，**正常用户的登录也会被拖死**。先做一次轻量的 Redis/DB 计数查询，就能在消耗算力之前把攻击挡掉。

### 时间攻击与用户枚举

```rust
// src/modules/auth/service.rs:100
let Some(credentials) = credentials else {
    let _ = verify_password_dummy(password).await;      // 照常算一次 Argon2
    Self::record_login_failure(db, redis, username, context.client_ip, window).await?;
    return Err(invalid_credentials());
};
```

如果用户不存在就立刻返回，响应时间会明显短于"用户存在但密码错"。攻击者用几万次请求统计耗时，就能枚举出哪些用户名真实存在——这是后续撞库的起点。

防御是**让两条路径耗时对齐**：

```rust
// src/modules/auth/service.rs:386
async fn verify_password_dummy(password: &str) -> Result<(), AppError> {
    tokio::task::spawn_blocking(move || {
        // 对比一个固定的合法哈希，校验结果本身没有意义，只取其计算耗时
        let _ = verify_password_blocking(&password, DUMMY_PASSWORD_HASH);
    }).await.map_err(|_| AppError::Internal("密码校验任务失败"))?;
    Ok(())
}
```

注意 `DUMMY_PASSWORD_HASH` 必须是**格式合法的 Argon2 输出**：

```rust
// src/modules/auth/service.rs:401
const DUMMY_PASSWORD_HASH: &str = "$argon2id$v=19$m=19456,t=2,p=1$AAAAAAAAAAAAAAAAAAAAAA$AAAA...";
```

如果它无法被解析，`verify_password_blocking` 会在计算开始前就失败返回，"不存在"分支反而更快——防护彻底失效。所以有一个专门的测试守着它：

```rust
// src/modules/auth/service.rs:628
fn dummy_password_hash_is_parseable() { assert!(PasswordHash::new(DUMMY_PASSWORD_HASH).is_ok()); }
```

> 这个测试是整个项目里最"反直觉但最有价值"的测试之一：**它守护的不是功能，而是一个安全前提。**

### 失败文案必须完全一致

```rust
// src/modules/auth/service.rs:285
fn invalid_credentials() -> AppError {
    AppError::Unauthorized("用户名或密码错误")
}
```

"用户不存在"和"密码错误"返回**同一个** 401 + 同一句话。任何差异（文案、状态码、响应头、耗时）都是枚举通道。

### 失败计数：Redis 是判定层，数据库是审计层

```rust
// src/modules/auth/service.rs:128
async fn count_login_failures(db, redis, username, window, window_start) -> Result<i64, AppError> {
    match redis.login_failure_count(username, window).await {
        Ok(count) => Ok(count),
        Err(error) => {
            tracing::warn!(%error, %username, "Redis 登录失败计数不可用，回退到数据库统计");
            Ok(AuthRepository::count_failures_since(db, username, window_start).await?)
        }
    }
}
```

这就是"降级策略写在 Service"的又一例：计数读 Redis（快、自动过期、多实例共享），失败时回退数据库（慢但准确）。限流**不会静默失效**。

```rust
// src/modules/auth/service.rs:142
async fn record_login_failure(db, redis, username, client_ip, window) -> Result<(), AppError> {
    AuthRepository::record_failure(db, username, client_ip).await?;   // 先写审计

    if let Err(error) = redis.record_login_failure(username, window).await {
        tracing::warn!(%error, %username, "Redis 登录失败计数写入失败，后续判定将回退到数据库统计");
    }
    Ok(())
}
```

写数据库失败会向上传播（审计丢了不行）；写 Redis 失败只告警（判定会自动回退）。**两种失败的不同处理，体现了"哪一个是权威"的判断。**

### 登录成功后为什么不清空计数

```rust
// src/modules/auth/service.rs:119
// 注意这里只清理数据库中的过期审计记录，不清空 Redis 中的窗口内计数：
// 成功登录不能证明之前的失败不是攻击行为，清空计数等于给攻击者一个
// 「只要偶尔成功一次就能重置限额」的入口。
AuthRepository::clear_failures_before(db, username, window_start).await?;
```

如果成功就清零，攻击者的策略变成"每猜 4 次密码，用已知正确的账号成功登录一次"，限额永远重置不了。这是个很细但很真实的设计。

### 窗口最小值兜底

```rust
// src/modules/auth/service.rs:293
fn rate_limit_window(auth_config: &AuthConfig) -> Duration {
    Duration::from_secs((auth_config.login_window_minutes * 60).max(60) as u64)
}
```

配置校验已经拒绝非正数，这里再 `max(60)` 是**防线内兜底**。为什么值得多写这一行？因为"窗口为 0"意味着所有失败记录立刻过期 = 限流被关闭，而且不会有任何报错。多一层保证比事后排查便宜得多。

## 9.6 登出：让唯一的凭据立刻失效

单令牌方案下，登出要撤销两类状态，但只有一类真正影响认证：

| 要撤销的东西 | 存在哪 | 作用 | 失败后果 |
| --- | --- | --- | --- |
| 会话审计记录（`revoked_at`） | PostgreSQL `user_sessions` | 回答"这次会话何时结束、来自哪个客户端" | 审计不完整，**认证不受影响** |
| 令牌本身（`jti`） | Redis 吊销列表 | 让令牌在自然过期前失效 | 令牌仍可用，直到 7 天后自然过期 |

```rust
// src/modules/auth/handler.rs:160
pub(crate) async fn logout(State(state): State<AppState>, headers: HeaderMap) -> Result<impl IntoResponse, AppError> {
    if let Some(token) = cookie::token_from_headers(&headers, &state.auth.cookie) {
        if let Err(error) = AuthService::logout(&state.db, &token).await {
            tracing::warn!(?error, "登出时吊销会话审计记录失败，仍继续清除客户端 Cookie");
        }
        if let Err(error) = AuthService::revoke_access_token(&state.redis, &state.jwt, &token).await {
            tracing::warn!(?error, "登出时写入令牌吊销列表失败，令牌将在自然过期前继续有效");
        }
    }
    // 即使没有令牌也返回成功：登出是幂等操作，
    // 重复调用或 Cookie 已缺失都不应让客户端收到错误。
    cleared_session_response(&state.auth.cookie, "登出成功")
}
```

三个设计点：

**① 两步都是"尽力而为"。** 任一吊销失败都只告警、继续清 Cookie。理由：让客户端卡在"无法退出"的状态，比一次吊销失败更糟；而且清掉 Cookie 本身已经能阻止这个浏览器继续使用令牌。

**② 唯一的 Cookie 就是全部输入。** 双令牌时代这里要读两个 Cookie、分别吊销两套状态，任何一个名字写错都会漏掉一半；现在只剩一个名字，取自 `auth.cookie.name`，读取与清除共用同一份配置。

**③ 幂等。** 没有令牌、令牌无效、会话不存在，一律返回成功：

```rust
// src/modules/auth/service.rs:167
pub async fn logout(db: &PgPool, token: &str) -> Result<(), AppError> {
    let token_hash = hash_token(token);
    let Some(session) = AuthRepository::find_session_by_token_hash(db, &token_hash).await? else {
        // 令牌无法对应任何会话，说明它从未被签发或已被清理。
        // 从调用方视角登出目标已达成，因此同样返回成功而不是报错。
        return Ok(());
    };
    AuthRepository::revoke_session(db, session.id).await?;
    Ok(())
}
```

注意这里**只用摘要、不解析令牌**。这不只是为了省一次验签，而是为了覆盖"令牌已经过期才登出"的场景：解析会失败，摘要不会——记录照样能被定位并关闭。否则过期后登出就退化成一次匿名请求，在审计表里留下一条永远不会关闭的会话。

### 令牌的立即吊销

```rust
// src/modules/auth/service.rs:187
pub async fn revoke_access_token(redis: &RedisStore, jwt_config: &JwtConfig, token: &str) -> Result<(), AppError> {
    let Ok(claims) = decode_access_claims(jwt_config, token) else {
        return Ok(());       // 解析不了：本来就通不过认证，不用吊销
    };

    let remaining = claims.exp - Utc::now().timestamp();
    if remaining <= 0 {
        return Ok(());       // 已过期：同上
    }

    redis.revoke_access_token(&claims.jti, Duration::from_secs(remaining as u64)).await
        .map_err(|error| { tracing::warn!(%error, "写入令牌吊销列表失败"); AppError::Internal("令牌吊销失败") })
}
```

**TTL = 令牌剩余有效期**，而不是固定值。令牌自然过期后吊销记录就没意义了，让它一起消失可以避免键无限累积。这两条"直接返回成功"的短路也很重要：写入一条永远不会被查询的记录只是浪费内存。

### 为什么不能让 `user_sessions` 承担这件事

最直觉的做法是"登出时把记录标成已吊销，之后每个请求都查一下这个摘要还在不在"。但那样每次请求都要访问一次数据库——JWT 带来的"无状态、少一次往返"就白拿了，而且多实例下这部分查询会直接压在 PostgreSQL 上。

Redis 吊销列表把这件事压成一次 `EXISTS`，键还会随令牌过期自动消失。代价是它**不是权威存储**：Redis 故障时认证中间件按"未吊销"放行，登出的令牌会一直可用到自然过期（见 8.3 与[第 10 章](./10-Redis与降级设计.md)）。这是刻意的降级方向——把缓存故障放大成"全员被踢下线"更糟。

认证中间件里的吊销检查（含降级分支）：

```rust
// src/common/auth.rs:79
async fn authenticate(state: &AppState, headers: &HeaderMap) -> Result<AuthUser, AppError> {
    let token = cookie::token_from_headers(headers, &state.auth.cookie)
        .ok_or(AppError::Unauthorized("未登录或登录已过期"))?;
    let verified = AuthService::verify_access_token(&state.jwt, &token)?;
    match state.redis.is_access_token_revoked(&verified.jti).await {
        Ok(true) => return Err(AppError::Unauthorized("认证令牌已失效，请重新登录")),
        Ok(false) => {}
        Err(error) => tracing::warn!(%error, "查询令牌吊销列表失败，按未吊销处理"),
    }
    Ok(AuthUser { user_id: verified.user_id })
}
```

三句 401 文案分别对应三种处境，客户端可以据此给出不同提示：

| 响应文案 | 触发条件 | 客户端该做什么 |
| --- | --- | --- |
| `未登录或登录已过期` | 请求里没有令牌 Cookie | 跳登录页 |
| `认证令牌已过期，请重新登录` | 令牌有效但 `exp` 已过 | 提示"登录已过期"，跳登录页 |
| `认证令牌已失效，请重新登录` | 令牌在 Redis 吊销列表里（登出过） | 清本地状态，跳登录页 |

## 9.7 Cookie：安全属性逐个说

```rust
// src/common/cookie.rs:47
pub fn build_token_cookie(config: &CookieConfig, value: &str, max_age_seconds: i64) -> String {
    Cookie::build((config.name.clone(), value.to_owned()))
        .path(config.path.clone())
        .http_only(true)                        // 固定启用，不可配置
        .secure(config.secure)                  // 生产必须 true
        .same_site(same_site(config))           // Strict 兜底
        .max_age(cookie::time::Duration::seconds(max_age_seconds))
        .build()
        .to_string()
}
```

注意签名里**没有 `name` 参数**：Cookie 名称只从 `config.name` 读取。双令牌时代这里要传名字进来（因为有两个名字），调用方写错名字就是"下发了一个客户端不会回传的 Cookie"，而这种错误在日志里几乎看不出来。把名字的唯一来源收进配置，下发与清除就不可能对不上。

| 属性 | 本项目取值 | 作用 |
| --- | --- | --- |
| `HttpOnly` | **固定 `true`** | 页面脚本无法读取令牌，XSS 只能"代为发请求"，无法窃取凭据长期冒用 |
| `Secure` | 配置控制（生产必须 `true`） | 只在 HTTPS 下发送 |
| `SameSite` | `Strict`（默认）/ `Lax` | 跨站请求不携带，防 CSRF 主防线 |
| `Path` | 配置，默认 `/` | 限制发送范围 |
| `Domain` | **刻意不设** | 省略时浏览器按"仅当前主机"处理，避免发到同父域的其他子域 |
| `Max-Age` | **等于令牌剩余有效期** | 默认 604800 秒（7 天），令牌失效时 Cookie 也一起消失 |
| `Name` | 配置，默认 `access_token` | 只有一个名字，读取、下发、清除共用同一份配置 |

**为什么不设 `Domain`？** 设成 `.example.com` 会让令牌发送给 `blog.example.com`、`api.example.com` 等所有子域；任何一个子域被攻破，令牌就泄露了。不设则只有当前主机能收到——更小的攻击面。

### `Max-Age` 与令牌有效期必须是同一个数

```rust
// src/modules/auth/handler.rs:73
fn session_response(cookie_config: &CookieConfig, issued: IssuedToken, message: &'static str) -> Result<axum::response::Response, AppError> {
    let mut headers = HeaderMap::new();
    append_set_cookie(&mut headers, build_token_cookie(cookie_config, &issued.token, issued.expires_in))?;
    let body = ApiResponse::success(message, AuthSessionResponse::new(issued.expires_in));
    Ok((headers, Json(body)).into_response())
}
```

`issued.expires_in` 同时喂给 Cookie 的 `Max-Age` 和响应体的 `expires_in`，所以两者不可能不一致。单令牌方案下这一点特别好保证：**只有一个令牌，只有一份剩余时间**。若 Cookie 比令牌活得久，浏览器会在令牌失效后继续发送它，服务端反复处理注定失败的请求；若 Cookie 先过期，用户会在令牌还有效时莫名掉登录。

### 清除 Cookie 的属性必须完全一致

```rust

        .http_only(true)

```

浏览器按 **名称 + 域 + 路径** 匹配 Cookie。属性不一致（比如下发时 `Path=/`、清除时 `Path=/api`）会导致清除失败，令牌残留在客户端——用户以为登出了，实际还能用。测试锁定了这条：

```rust
// src/common/cookie.rs:180
fn clear_cookie_matches_issued_attributes() { /* 断言 Max-Age=0、HttpOnly、SameSite、Path 一致 */ }
```

### 为什么只接收 Cookie，不接收 `Authorization` 头

两个原因：

1. **旁路**：如果两种方式都支持，攻击者/客户端可以用 `Authorization` 绕开 `HttpOnly`、`SameSite` 这些只为 Cookie 设计的保护。
2. **一致性**：只保留一条认证路径，不存在"某条路径漏校验 Cookie"的差异化实现空间。

### 解析：多个同名 Cookie 怎么办

```rust
// src/common/cookie.rs:14
fn cookie_value(headers: &HeaderMap, name: &str) -> Option<String> {
    for header_value in headers.get_all(axum::http::header::COOKIE) {
        let Ok(raw) = header_value.to_str() else { continue; };   // 单个头非法就跳过
        for cookie in cookie::Cookie::split_parse(raw.to_owned()).flatten() {
            if cookie.name() == name { return Some(cookie.value().to_owned()); }
        }
    }
    None
}
```

注意两点：**遍历所有 `Cookie` 头**（浏览器可能拆成多个头），**遇到非法头继续而不是整体失败**（其他 Cookie 里可能还有有效令牌）。

## 9.8 CSRF：三层防御

Cookie 会自动随请求发送，这是它的便利也是它的风险。

| 层 | 措施 | 作用 |
| --- | --- | --- |
| 1（主） | `SameSite=Strict` | 跨站请求完全不携带令牌 Cookie |
| 2 | 写操作全部 `POST` + 强制 `application/json` | 浏览器对 `application/json` 的跨源请求会先发预检（`OPTIONS`），而 CORS 不会放行未授权来源 |
| 3 | 没有"用 GET 改状态"的接口 | 顶层 GET 导航不受 SameSite=Strict 保护，但当前没有副作用 |

放宽到 `Lax` 的残余风险要明确：外部站点的顶层 GET 导航会带 Cookie。当前所有写操作都是 POST，所以不影响认证状态——**但这是"当前恰好成立"，不是永远成立**。将来若加了 `GET /auth/logout` 这类接口，Lax 就有风险了。

| `does_not_whitelist_removed_refresh_route` | `common/auth.rs:130` | 已下线的 `/auth/refresh` 不能留在白名单里 |
| `keeps_login_reachable_without_token` | `app/mod.rs:315` | 登录匿名可达 |
| `keeps_logout_reachable_without_token` | `app/mod.rs:289` | 登出匿名可达且幂等 |
| `returns_not_found_for_removed_refresh_route` | `app/mod.rs:301` | `/auth/refresh` 返回 404，不再能换令牌 |

## 9.10 生产环境必须做的三件事

| 事项 | 不做会怎样 |
| --- | --- |
| 替换 `APP__JWT__SECRET` | 配置文件里是公开的占位值；使用它等于任何人都能伪造任意用户令牌。长度校验能拒短密钥，但**识别不了已泄露的长密钥** |
| `APP__AUTH__COOKIE__SECURE=true` | 令牌在明文 HTTP 中传输，可被中间人截获 |
| 各实例 `jwt.secret` 一致 | 令牌在实例间随机失效，表现为用户"时好时坏地掉登录" |

以及：引导账号创建完成后关闭 `bootstrap.enabled` 并从部署环境移除凭据。

## 9.11 动手练习

1. **解码自己的令牌**：登录后从 `cookies.txt` 取 `access_token`（名字来自 `auth.cookie.name`），用 `jwt.io` 或本地脚本解码，对照 `AccessClaims` 逐字段确认——尤其是 `exp - iat` 应该等于 `jwt.ttl_minutes` 的 604800 秒。
2. **验证吊销**：登录 → 登出 → 用同一个 `access_token` 访问 `/auth/me`，期望 401 `认证令牌已失效，请重新登录`。然后停掉 Redis、重新登录再重复一次，期望登出后**仍然能通过**（降级为"到期才失效"）——这就是把"立即失效"做成增强而非前提的代价。
3. **确认刷新入口真的下线**：`curl -i` 登录一次，数一数响应里有几个 `Set-Cookie`（应为 1）；再 `POST /api/v1/auth/refresh`（带与不带 Cookie 各一次），两者都应返回 `404`（业务码 `40400`）。最后读 `common::auth` 的 `PUBLIC_PATHS`，确认长度是 2。
4. **制造时间攻击对照组**：写一个小脚本，分别用"不存在的用户名"和"存在但密码错"各请求 50 次，记录平均耗时。两者应在同一量级（差异主要来自网络抖动）。
5. **加一条安全断言**：给 `decode_access_claims` 加一个 `aud`（受众）声明并校验，写出对应测试。思考：多服务共用密钥时，`aud` 比 `iss` 多解决什么问题？
6. **观察过期路径**：用 `APP__JWT__TTL_MINUTES=1` 启动，登录后等 61 秒再访问 `/auth/me`，确认文案是 `认证令牌已过期，请重新登录` 且**没有任何可以续期的接口**。再把 `ttl_minutes` 改回 10080，体会"有效期是唯一能控制泄露窗口的旋钮"。
