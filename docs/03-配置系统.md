# 03 配置系统

**本章目标**：理解"配置为什么必须强类型 + 启动期校验"，并掌握本项目四级配置覆盖的规则。配置是后端的生死线——**90% 的线上事故不是代码写错，而是配置和代码的假设不一致**。

---

## 3.1 反例先行：弱类型配置的三种死法

```rust
// 你可能见过的写法
let port = env::var("PORT").unwrap_or("3000".into()).parse().unwrap();
let secret = env::var("JWT_SECRET").unwrap_or("secret".into());
```

三种死法：

1. **运行期才炸**：`parse()` 在第一次用到时 panic，而调用点在某个低频接口里 → 上线三天才发现。
2. **默认值变成生产值**：忘了设 `JWT_SECRET`，服务用 `"secret"` 签令牌，任何人都能伪造任意用户身份。
3. **拼写错误静默生效**：把 `DATABASE_URL` 写成 `DATABSE_URL`，取到 `None`，然后用了兜底默认值连上了错误的库。

本项目的对策是把三件事拆开，各用最强的工具：

| 问题 | 工具 | 本项目位置 |
| --- | --- | --- |
| 配置从哪来、怎么覆盖 | `config` crate 的分层 | `src/config/mod.rs:149` |
| 配置值是什么类型 | `serde` 反序列化到强类型结构 | `src/config/mod.rs:7` |
| 配置合不合法 | 启动期 `validate()` | `src/config/mod.rs:175` |

于是业务代码只依赖**已经反序列化好的强类型配置**，全局搜索 `env::var` 只会在 `src/config/mod.rs` 里出现一次。

## 3.2 四级覆盖：从默认值到部署环境

```rust
// src/config/mod.rs:149
pub fn new() -> Result<Self, ConfigError> {
    dotenvy::dotenv().ok();                                    // 加载 .env（可选）
    let run_mode: String = env::var("RUN_MODE").unwrap_or_else(|_| "development".into());

    let config: Config = Config::builder()
        .add_source(File::with_name("config/default"))          // ① 默认值，必存在
        .add_source(File::with_name(&format!("config/{}", run_mode)).required(false))  // ② 环境差异
        .add_source(File::with_name("config/local").required(false))                   // ③ 本地覆盖
        .add_source(Environment::with_prefix("APP").separator("__"))                   // ④ 环境变量
        .build()?;

    config.try_deserialize()
}
```

**后加载的覆盖先加载的**，优先级从低到高：`default.toml` → `{RUN_MODE}.toml` → `local.toml` → `APP__*` 环境变量。

这种设计回答了一个部署时的常见问题："生产环境的值到底写在哪？"

| 值 | 写在哪 | 理由 |
| --- | --- | --- |
| 端口、超时、TTL、分页上限 | `config/default.toml` | 与环境无关，改了要能一起发布 |
| 主机、连接数、日志级别 | `config/{RUN_MODE}.toml` | 按环境差异调整 |
| 数据库密码、JWT 密钥、引导账号口令 | **`APP__*` 环境变量** 或 `config/local.toml` | 属于凭据，不能进版本控制 |
| 本地调试的临时覆盖 | `config/local.toml` | 已被 `.gitignore` 排除 |

环境变量用双下划线表示层级：

```bash
APP__SERVER__PORT=8080
APP__DATABASE__URL=postgresql://user:pass@host/db
APP__AUTH__COOKIE__SECURE=true
APP__BOOTSTRAP__PASSWORD='强口令'
```

`APP__AUTH__COOKIE__SECURE` 对应 `auth.cookie.secure`：`APP__` 是前缀，`__` 是一层，单下划线是字段名的一部分（所以 `MAX_LOGIN_FAILURES` 不会被误拆）。

> **已知小坑**：`.env.example` 里写的是 `RUN_MODE=default`。而 `RUN_MODE` 默认值本来就是 `development`，`config/default.toml` 又是无条件加载的第一层——写成 `default` 会让同一个文件被加载两次。这**不会出错**（后加载的相同值覆盖前面），但语义上应该写 `development` 或 `production`。学习时可以改成 `development` 体会差异。

## 3.3 配置结构：一一对应，不猜不拼

配置结构体和 TOML 文件严格对应，读起来可以互相印证。

### 顶层

```rust
// src/config/mod.rs:7
pub struct AppConfig {
    pub server: ServerConfig,
    pub database: DatabaseConfig,
    pub log: LogConfig,
    pub redis: RedisConfig,
    pub jwt: JwtConfig,
    pub auth: AuthConfig,
    pub bootstrap: BootstrapConfig,
}
```

### 各段职责

| 结构 | 字段 | 说明 |
| --- | --- | --- |
| `ServerConfig` | `host`、`port` | `server_address()`（`:167`）拼成 `host:port` |
| `DatabaseConfig` | `url`、`max_connections` | 连接池上限，不是"每请求一条" |
| `LogConfig` | `level` | 直接作为 `EnvFilter` 的表达式，可用 `info,sqlx=warn` 这类语法 |
| `RedisConfig` | `url`、`pool_size`、`key_prefix`、`user_cache_ttl_seconds` | 键前缀是多环境隔离的唯一手段 |
| `JwtConfig` | `secret`、`issuer`、`access_ttl_minutes`、`refresh_ttl_days` | 双令牌的两套有效期 |
| `AuthConfig` | `max_login_failures`、`login_window_minutes`、`cookie` | 登录保护 + Cookie |
| `BootstrapConfig` | `enabled`、`username`、`email`、`password`、`nickname` | 一次性引导账号 |

两个细节值得单独说：

```rust
// src/config/mod.rs:139  可选字段必须显式 default
#[serde(default)]
pub nickname: Option<String>,
```

配置里省掉 `nickname` 时按 `None` 处理。**注意 `Option<T>` 在 serde 里默认并不是"缺失即 None"**——不写 `#[serde(default)]`，缺字段会反序列化失败。这是新手很常见的坑。

```rust
// src/config/mod.rs:66  access token 有效期为什么短
/// access token 有效期（分钟）。取值较短，因为无状态令牌无法单独吊销。
pub access_ttl_minutes: i64,
```

配置项旁边的注释解释了**为什么**是 15 分钟而不是随便取个数——因为无状态令牌在服务端不保存状态，只能靠短有效期缩小泄露窗口。这类"配置值背后有设计原因"的注释比"有效期"三个字有用得多。

## 3.4 启动期校验：把问题挡在监听之前

```rust
// src/config/mod.rs:175
pub fn validate(&self) -> Result<(), ConfigError> {
    if self.jwt.secret.len() < MIN_JWT_SECRET_LENGTH {
        return Err(ConfigError::Message(format!(
            "JWT 密钥长度不得少于 {MIN_JWT_SECRET_LENGTH} 个字符"
        )));
    }
    // ... 其余 8 条
}
```

设计原则写在注释里（`:171-174`）：**在启动阶段就拒绝弱密钥，而不是打印告警继续运行**。一旦以弱密钥上线，攻击者可以离线伪造任意用户的令牌，运行期再发现已经太晚。

完整校验清单：

| 校验 | 拒绝的原因 |
| --- | --- |
| `jwt.secret` 长度 ≥ 32 | HS256 安全性完全依赖密钥熵，短密钥可被离线爆破 |
| `access_ttl_minutes`、`refresh_ttl_days` > 0 | 零或负有效期令牌立刻失效，等于全员无法登录 |
| `max_login_failures`、`login_window_minutes` > 0 | 非正数会让限流变成"永远拒绝"或"永不触发" |
| `cookie.access_name`、`refresh_name` 非空 | 空名字的 Cookie 无法下发 |
| 两个 Cookie 名**不相同** | 同名会互相覆盖，登录后刷新令牌直接丢失 |
| `redis.url` 以 `redis://` 或 `rediss://` 开头 | 写错协议时运行期只会静默降级，排障极难联想到配置 |
| `redis.pool_size` > 0 | 池大小为 0 永远取不到连接 |
| `redis.key_prefix` 非空 | 空前缀会让多环境互相覆盖限流计数与吊销记录 |
| `redis.user_cache_ttl_seconds` > 0 | 非正数会让缓存永不过期 |
| `bootstrap.enabled` 时三个字段非空 | 否则"服务已启动但没人能登录" |

注意最后一条的**边界克制**：

```rust
// src/config/mod.rs:224
// 这里只做非空检查，长度、邮箱格式等细则由创建用户请求模型的校验统一负责，
// 避免同一套规则在配置层和第二份实现中逐渐分叉。
```

配置层只检查"非空"，用户名 3–50、邮箱格式、密码 8–72 这些细则交给 `CreateUserRequest` 的 `validator` 规则。**同一套规则只能有一份实现**，否则两边迟早不一致（比如密码上限从 72 改成 128 时只改了一处）。

## 3.5 Fail-safe：配置写错时要更严格，不能更宽松

```rust
// src/config/mod.rs:109
pub fn same_site_attribute(&self) -> &'static str {
    if self.same_site.eq_ignore_ascii_case("lax") {
        "Lax"
    } else {
        "Strict"   // 任何未知取值都回退到最严格
    }
}
```

`same_site = "none"` 或 `same_site = "stdict"` 都会回退到 `Strict`。这不是"宽松处理"，而是**保守处理**：配置写错的风险方向必须是"更安全"，不能是"防护被静默关闭"。

对照一下反例：如果实现成 `match` 加 `_ => "None"`，一次拼写错误就会让 CSRF 防护全线失效，而且**没有任何报错**。

这条原则在本项目里反复出现，记住它：

> 当配置值非法时，默认行为要落在"限制更多"一侧，而不是"限制更少"一侧。

## 3.6 凭据的归属

`config/default.toml` 会提交到仓库，所以里面的值全部是占位值：

```toml
# config/default.toml
[jwt]
secret = "dev-only-insecure-secret-change-me-32chars"   # 公开的占位值
```

```toml
# config/local.toml（.gitignore 排除，不提交）
[bootstrap]
enabled = true
password = "真实的强口令"
```

生产环境必须做三件事（[reference/AUTH_API.md](./reference/AUTH_API.md) 有完整清单）：

1. 用环境变量替换 `APP__JWT__SECRET`（`openssl rand -base64 48` 生成）。长度校验能拒绝短密钥，但**无法识别"已泄露的长密钥"**。
2. `APP__AUTH__COOKIE__SECURE=true`，否则令牌在明文 HTTP 中传输。
3. 多实例部署时保证各实例 `jwt.secret` 一致，否则令牌在实例间随机失效。

## 3.7 动手练习

1. **验证优先级**：不设任何环境变量，启动后看 `/` 返回的端口行为；然后 `$env:APP__SERVER__PORT=3999; cargo run` 再启动，确认环境变量赢了。
2. **触发一次启动失败**：把 `jwt.secret` 改成 `"short"` 启动，记录完整报错；再试 `redis.url = "http://127.0.0.1:6379"`，对比两条错误的信息质量。
3. **加一个配置项**：给 `ServerConfig` 加 `request_timeout_seconds: u64`，在 `config/default.toml` 里补默认值，在 `validate()` 里校验它 > 0，然后跑 `cargo test` 看有多少测试因为结构体字面量缺字段而失败。这个失败恰好说明了"强类型配置"的价值：**新增必填字段时，所有构造点都会被编译器点名。**
4. **体会 fail-safe**：把 `same_site_attribute` 改成 `if lax { "Lax" } else if strict { "Strict" } else { "None" }`，然后跑 `src/config/mod.rs` 里的单元测试 `falls_back_to_strict_same_site`，看它如何拦住这个改动。
