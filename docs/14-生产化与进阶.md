## 14.1 上线前的安全清单

按"不做会怎样"排序，全部来自本项目的真实配置与代码：

| # | 事项 | 不做会怎样 | 怎么改 |
| --- | --- | --- | --- |
| 1 | 替换 `jwt.secret` | 配置里是公开占位值，任何人可伪造任意用户令牌 | `APP__JWT__SECRET=$(openssl rand -base64 48)` |
| 2 | 多实例 `jwt.secret` 一致 | 令牌在实例间随机失效，用户"时好时坏掉登录" | 用同一个密钥来源（K8s Secret / 密钥管理服务） |
| 3 | `auth.cookie.secure = true` | 令牌在明文 HTTP 中可被中间人截获 | `APP__AUTH__COOKIE__SECURE=true`，并确保有 TLS |
| 4 | 关闭 `bootstrap.enabled` | 遗留一个口令人工设定、权限等于普通用户的账号 | 建号后改回 `false` 并从环境移除凭据 |
| 5 | 收紧 CORS | 当前 `allow_origin(Any)`，跨源部署时既不能用凭据也别想安全 | 指定具体前端来源 + `allow_credentials(true)` |
| 6 | 每个环境独立 `redis.key_prefix` | 多环境共用实例时互相覆盖限流计数与吊销记录 | 按环境设置，如 `axum-prod` |
| 7 | PostgreSQL `lc_messages = 'C'` | SQLx 无法解析错误，所有数据库错误变成"协议错误"，排障灾难 | 见[reference/ARCHITECTURE.md](./reference/ARCHITECTURE.md) 第 4 节 |
| 8 | 迁移在发布流程中先行验证 | 迁移失败会阻止启动，但也意味着旧版本还在跑新结构 | 在预发环境先跑一次 |
| 9 | 日志级别不设为 `debug` | `sqlx` 的 debug 日志会打印 SQL 与参数（含敏感数据） | `log.level = "info,sqlx=warn"` |
| 10 | 数据库账号最小权限 | 应用账号能 `DROP TABLE` | 只给业务表 DML + 迁移账号单独授权 |

### 一个容易忽略的点：口令的去向

`bootstrap.password` 是明文口令，它存在：

1. 环境变量 / `config/local.toml`（部署系统里可见）
2. **进程内存中的 `AppConfig`**，整个生命周期都在
3. 引导账号创建后会被 Argon2 哈希写入数据库，但**明文仍留在配置结构里**

严格的实现会在创建成功后把 `config.bootstrap.password` 清空（需要 `&mut` 或 `take()`）。当前没做——对一个"建完就关开关"的一次性功能来说，风险可以接受，但你应该知道它的存在。这是"阅读理解代码"和"审阅代码"的区别。

## 14.2 性能与容量

| 维度 | 现在怎么做的 | 什么时候该改 |
| --- | --- | --- |
| 数据库连接池 | `max_connections` = 10（dev）/ 20（prod） | 实例数 × 池大小 接近数据库 `max_connections` 时，改用 PgBouncer |
| 取连接超时 | 10 秒 | 超过 1 秒没拿到连接通常说明池太小或库太慢，可以调小以快速失败 |
| Redis 池 | 8（dev）/ 16（prod），多路复用 | 一般不用调大，先看命令数能不能合并 |
| 分页 | `LIMIT/OFFSET` | 单表超过百万行且需要深翻页 → 游标分页 |
| 索引 | 每个高频查询都有对应索引 | 加索引前先 `EXPLAIN ANALYZE` 确认真的用得上 |
| CPU 密集 | 密码哈希走 `spawn_blocking` | 如果将来加了图片处理、PDF 生成，同样必须 `spawn_blocking` |
| 日志量 | 请求级 span + 关键事件 | QPS 上千后要采样，否则 I/O 成为瓶颈 |
| 响应压缩 | **未启用** | 大 JSON 响应 → 加 `tower-http` 的 `CompressionLayer` |
| 超时 | **只有取连接超时** | 上线前应加请求级超时，避免慢请求堆积（见 14.3） |

### 容量估算的一个简单算法

```text
假设：单实例 500 QPS，每请求平均 3 次 SQL，每次 SQL 2ms
每个 SQL 占用连接时长 ≈ 2ms + 应用处理 1ms ≈ 3ms
需要的并发连接数 ≈ 500 × 3 × 3ms / 1000ms ≈ 4.5
→ 池大小 10 足够，瓶颈通常在数据库 CPU 而非连接数
```

**结论先行**：绝大多数中小项目的瓶颈不是连接池大小，而是缺失的索引和 N+1 查询。先把 `EXPLAIN` 看懂，再谈调参。

## 14.3 部署形态与已知缺口

### 部署到生产的三条硬要求

```text
1. 配置全部来自环境变量（12-factor），镜像里不含任何凭据
2. 迁移随二进制发布并在启动时执行（本项目已满足：sqlx::migrate! 编译期嵌入）
3. 探针配对正确：liveness → /health，readiness → /ready
```

### 本项目目前**没有**做的事（诚实清单）

| 缺口 | 风险 | 补齐方式 |
| --- | --- | --- |
| **没有优雅停机** | 收到 SIGTERM 后进程直接退出，**正在处理的请求被截断** | `axum::serve(...).with_graceful_shutdown(shutdown_signal())`，配合编排系统的 `terminationGracePeriodSeconds` |
| 没有请求级超时 | 慢请求可以长期占用连接 | `tower_http::timeout::TimeoutLayer` |
| 没有全局速率限制 | 只是登录有限流，其他接口可被刷 | 按 IP / 用户加通用限流（Redis 计数器） |
| 没有 metrics / 告警 | 无法做 QPS、P99、错误率看板 | `axum-prometheus` 或 OpenTelemetry |
| 没有 RBAC | 登录即可访问全部业务接口 | 加 `roles`/`permissions` 表 + 中间件校验（见 14.4） |
| `users.email` 不是 UNIQUE | 同一邮箱可注册多个账号 | 新增迁移加唯一索引（先清理重复数据） |
| 会话/失败记录无清理任务 | `user_sessions`、`login_failures` 会持续增长 | 定时任务或用部分索引 + 归档 |
| 没有 `X-Forwarded-For` 支持 | 部署在代理后时审计 IP 全是代理地址 | 确认代理可信后读取并校验该头 |
| `RUST_LOG` 不生效 | 与常见习惯不一致 | `EnvFilter::from_default_env()` 再叠加配置指令 |
| 没有 CI 配置 | 格式/clippy/测试靠人工 | 加 GitHub Actions：`fmt --check && clippy -D warnings && test` |

**优雅停机为什么排第一？** 因为它在滚动发布时**每次都会发生**：K8s 发 SIGTERM → 进程立刻死 → 正在执行的 INSERT/UPDATE 被中断。对客户端表现为随机的 502/连接重置，而且很难复现。恢复成本最低、收益最直接。

一个最小实现（可以直接用）：

```rust
// src/main.rs 的末尾替换 serve 那一行（示意，未在本项目中实现）
use tokio::signal;

async fn shutdown_signal() {
    let ctrl_c = async { signal::ctrl_c().await.expect("无法监听 Ctrl+C") };

    #[cfg(unix)]
    let terminate = async {
        signal::unix::signal(signal::unix::SignalKind::terminate())
            .expect("无法监听 SIGTERM")
            .recv()
            .await;
    };
    #[cfg(not(unix))]
    let terminate = std::future::pending::<()>();

    tokio::select! {
        _ = ctrl_c => {},
        _ = terminate => {},
    }
    tracing::info!("收到停止信号，等待进行中的请求完成");
}

axum::serve(listener, app.into_make_service_with_connect_info::<std::net::SocketAddr>())
    .with_graceful_shutdown(shutdown_signal())
    .await?;
```

## 14.4 授权怎么做：从"能认证"到"能授权"

当前模型只有一个隐式角色：**登录 = 全权**。要加真正的授权，最小可行方案是：

```text
1. 数据：users.role VARCHAR + permissions 表（或 role_permissions 关联表）
2. 令牌：在 AccessClaims 里加 role（注意：改声明会影响所有已签发令牌，需过渡期）
3. 中间件：require_role("admin")，与 require_login 同样的"默认拒绝"思路
4. 数据层：继续坚持"归属写进 WHERE"——这是最可靠的授权形式
```

两条经验：

- **不要只靠中间件做授权。** 中间件保护的是"接口"，但"这条数据属于谁"必须由 SQL 保证。第 13 章的 `AND user_id = $2` 就是最简单的授权。
- **不要在设计里区分 401 和 403 的原因细节。** 401 是"没登录"，403 是"登录了但没权限"。对"资源存在但不是你的"这种情况，返回 404 更安全。

### 三条学习建议

**① 从"改这个项目"开始，而不是从"读教程"开始。** 上面每个主题都能在本项目里找到落点：加优雅停机只用改 `main.rs` 一处，加超时只用加一个 layer。

**② 每加一个功能，先写"失败时会怎样"。** 这是本项目贯穿始终的思维方式——Redis 挂了、库挂了、令牌过期、并发写入，每一种都要有明确答案。这个习惯比任何框架知识都值钱。

**③ 读别人的错误处理和降级代码。** 业务逻辑各项目不同，但错误处理和降级是通用能力。你在这个项目里看到的 `warn!` + 继续、`&'static str` 提示语、`ConnectInfo` 的 `Option`、`without_connection()`，都是可以直接搬到下一个项目的模式。

## 14.7 动手练习（收尾）

1. **加优雅停机**：按 14.3 的代码改装 `main.rs`，然后用一个慢请求（比如给 `hello_handler` 加 `tokio::time::sleep(5s)`）配合 `Ctrl+C` 验证：信号发出后请求仍然完成了。
2. **加请求超时**：在 `create_app` 里加 `tower_http::timeout::TimeoutLayer::new(Duration::from_secs(10))`，然后用上面的 sleep 验证超时被触发、返回什么状态码。思考：超时后业务操作会不会继续执行？这对事务意味着什么？
3. **补上 email 唯一约束**：写 `004_unique_email.sql`，先在开发库清理重复邮箱，再加唯一索引，然后让 Service 把冲突转成 409 `邮箱已被使用`。注意 `is_unique_violation()` 无法区分是 username 还是 email 冲突——你打算怎么区分？
4. **写一份自己的上线检查清单**：把 14.1 的表复制出来，逐项标注"本项目是否满足"，不满足的写下补齐计划。
5. **给你的笔记模块加 metrics**：统计创建/删除次数（先用 `tracing::info!(metric = "note_created")` 打点，再考虑接入真正的 metrics 库）。
