# 08 全局状态与中间件

**本章目标**：搞懂两件事——"多个 Handler 怎么共享数据库池和配置"（状态），以及"公共逻辑（认证、日志、CORS）怎么挂在所有接口上"（中间件）。这两者是 Axum 里最容易写对但最难写好的部分。

---

## 8.1 `AppState`：共享依赖的正确姿势

```rust
// src/app/state.rs:17
#[derive(Clone)]
pub struct AppState {
    pub db: PgPool,          // PostgreSQL 连接池
    pub redis: RedisStore,   // Redis 适配层
    pub jwt: Arc<JwtConfig>, // JWT 配置
    pub auth: Arc<AuthConfig>,// 认证/Cookie 配置
}
```

### 为什么可以每请求克隆

Axum 会为每个请求克隆一次 `State`。这不贵，因为四个字段都是**共享句柄**：

| 字段 | 内部结构 | 克隆成本 |
| --- | --- | --- |
| `PgPool` | `Arc` 包着的连接池 | 加一次引用计数 |
| `RedisStore` | `bb8::Pool<Client>` + `String` + `Duration` | 同上（`String` 复制长度很小） |
| `Arc<JwtConfig>` | 引用计数 | 极低 |
| `Arc<AuthConfig>` | 引用计数 | 极低 |

**判断标准**：克隆时复制的是"句柄"还是"数据"？句柄便宜，大块数据不便宜。本项目所有字段都在便宜那一侧。

### 为什么配置用 `Arc`

```rust
// src/app/state.rs:10
/// 认证配置随状态共享：提取器需要在校验令牌时访问 JWT 密钥，
/// 若通过参数逐层传递会让每个需要认证的 Handler 都多一个依赖参数。
```

`Arc<JwtConfig>` 有两个作用：

1. 让认证中间件能直接通过 `State` 拿到 JWT 密钥，不必给每个受保护 Handler 加参数。
2. 避免每次克隆状态都复制整个配置结构（含两个 `String`）。一次请求的差别微不足道，但这是**正确的直觉**。

### 为什么不用全局变量

| 方案 | 问题 |
| --- | --- |
| `static DB_POOL: OnceCell<PgPool>` | 测试之间互相污染；无法为不同测试用不同配置；初始化顺序隐式 |
| `lazy_static` / `OnceLock` 放配置 | 同上，且依赖变成"隐式可见"，读 Handler 签名看不出它用了什么 |
| **`AppState` 通过 `State` 提取**（本项目） | 依赖显式出现在签名里，可测试、可替换 |

```rust
// src/app/state.rs:26
pub fn new(db_pool: PgPool, redis: RedisStore, jwt: JwtConfig, auth: AuthConfig) -> Self { ... }
```

构造函数收"已经构造好的组件"，而不是自己根据配置去连库。这样 `create_app` 能在启动流程里明确报告"哪个组件初始化失败"，测试里也能塞假组件（`RedisStore::without_connection()`）。

## 8.2 中间件：把横切逻辑挂在路由组上

### 三层结构

```text
请求
  ↓
日志层 TraceLayer          ← app/mod.rs:33（最后加，所以最外层）
  ↓
CORS 层                     ← app/mod.rs:31
  ↓
路由匹配
  ├─ /health /ready        → 匿名 Handler
  ├─ /swagger-ui           → 匿名 Handler
  └─ /api/v1/**            → 认证中间件 ← app/routes.rs:40
                                ↓
                             Handler
```

**顺序很关键**：Axum 里 `.layer(a).layer(b)` 中 `b` 更外层（后加的包在外面）。所以 `create_app` 里先 `.layer(cors_layer())` 再 `.layer(logging_middleware())`，含义是：

```text
日志层（最外）→ CORS → 路由 → 认证 → Handler
```

为什么这样排？

- **日志最外**：能记录所有请求，包括被 CORS 和认证拒绝的。否则 401 风暴在日志里完全不可见。
- **CORS 在认证外**：浏览器的预检请求（`OPTIONS`，不带 Cookie）必须在认证之前被处理，否则永远过不了 401。
- **认证在路由组内层**：只保护 `/api/v1`，不影响健康检查。

### 日志中间件：交给 `tower-http`

```rust
// src/app/middleware.rs:46
pub fn logging_middleware() -> TraceLayer<SharedClassifier<ServerErrorsAsFailures>> {
    TraceLayer::new_for_http()
        .make_span_with(DefaultMakeSpan::new().level(Level::INFO))
        .on_response(DefaultOnResponse::new().level(Level::INFO).latency_unit(LatencyUnit::Millis))
}
```

文件里还保留了一份**手写版本**作为参考（`src/app/middleware.rs:26-45`，`ignore` 块里的代码不会编译），展示了中间件的原始形态：

```rust
pub async fn logging_middleware(request: Request, next: Next) -> Response {
    let method = request.method().clone();
    let uri = request.uri().clone();
    let start = Instant::now();

    let response = next.run(request).await;      // ← 调用链继续

    tracing::info!(%method, %uri, status = response.status().as_u16(),
                   duration_ms = start.elapsed().as_secs_f64() * 1000.0, "request completed");
    response
}
```

看懂这段就理解了中间件的本质：

> **中间件 = 拿到请求 + 调用 `next.run(request)` + 处理响应。**

`next.run()` 之前是"请求阶段"，之后是"响应阶段"，两者都可以做事情（改头、记日志、拦请求）。`TraceLayer` 只是把这个模式做得更完善（自动建 span、把状态码和耗时挂在同一个 span 上）。

### CORS：一个必须配合 Cookie 的坑

```rust
// src/app/middleware.rs:60
pub fn cors_layer() -> CorsLayer {
    CorsLayer::new().allow_origin(Any).allow_methods(Any).allow_headers(Any)
}
```

当前配置放行任意来源，只适合开发。**一旦前后端跨源部署，必须改**：

| 约束 | 原因 |
| --- | --- |
| 不能用 `Any` 来源 | 浏览器在凭据模式（`credentials: 'include'`）下**拒绝通配来源** |
| 必须 `allow_credentials(true)` | 否则浏览器不会发送/接收 Cookie |
| 必须指定具体来源 | 与上一条配合 |

不改的典型症状：**登录接口返回 200，但下一个接口全是 401**——因为浏览器根本没把 `Set-Cookie` 的令牌带回来，而服务端日志看起来一切正常（登录确实成功了）。这个 bug 极耗时间，因为两边日志都对。

## 8.3 认证中间件精读

```rust
// src/common/auth.rs:63
pub async fn require_login(State(state): State<AppState>, request: Request, next: Next)
    -> Result<Response, AppError>
{
    if is_public_path(request.uri().path()) {
        return Ok(next.run(request).await);       // 白名单直接放行
    }

    let user = authenticate(&state, request.headers()).await?;   // 失败 → 401，不进 Handler

    let (mut parts, body) = request.into_parts();     // 拆开请求
    parts.extensions.insert(user);                    // 写入身份
    Ok(next.run(Request::from_parts(parts, body)).await)  // 重新组装
}
```

### 白名单：三个常量，一处维护

```rust
// src/common/auth.rs:40
pub const LOGIN_PATH: &str = "/auth/login";
pub const REFRESH_PATH: &str = "/auth/refresh";
pub const LOGOUT_PATH: &str = "/auth/logout";

// src/common/auth.rs:57
const PUBLIC_PATHS: [&str; 3] = [LOGIN_PATH, REFRESH_PATH, LOGOUT_PATH];
```

这三项每一项都有不可移除的理由：

| 路径 | 为什么必须匿名 |
| --- | --- |
| `/auth/login` | 登录本身要匿名，否则拿不到凭证 |
| `/auth/refresh` | access token 过期后客户端只剩刷新 Cookie，否则刷新永远无法启动 |
| `/auth/logout` | 登出必须幂等；令牌已失效时仍要能清会话 |

**注册路由和写白名单用的是同一组常量**：

```rust
// src/modules/auth/handler.rs:32
Router::new()
    .route(LOGIN_PATH, post(login))
    .route(REFRESH_PATH, post(refresh_token))
    .route(LOGOUT_PATH, post(logout))
    .route("/auth/me", get(current_user))
```

这是防"路由改了、白名单没改"的关键。如果两处各写字符串，一次改名就能造成"登录接口要求登录"的死循环。

### 路径匹配：为什么要同时接受两种形式

```rust
// src/common/auth.rs:83
fn is_public_path(path: &str) -> bool {
    let relative_path = path.strip_prefix(API_PREFIX).unwrap_or(path);
    PUBLIC_PATHS.contains(&relative_path)
}
```

因为 `nest("/api/v1", ...)` 会剥离前缀（见[第 05 章](./05-请求生命周期.md)），中间件在真实请求里看到的是 `/auth/login`。但人读代码、对文档核对时写的是 `/api/v1/auth/login`。两种都接受，避免"照文档写白名单"的人写出静默失效的代码。

注意是**完全相等**匹配，不是 `starts_with`：

```rust
// src/common/auth.rs:149  测试锁定了这个行为
assert!(!is_public_path("/auth/login/extra"));
assert!(!is_public_path("/auth/logins"));
```

如果用前缀匹配，将来出现 `/auth/login/xxx` 子路由就会成为匿名入口。

### 身份传递：扩展（extensions）

```rust
// src/common/auth.rs:34
#[derive(Debug, Clone, Copy)]
pub struct AuthUser {
    pub user_id: i64,
}
```

中间件把 `AuthUser` 塞进请求扩展，Handler 用提取器取出来：

```rust
// src/common/auth_extractor.rs:21
impl FromRequestParts<AppState> for CurrentUser {
    type Rejection = AppError;

    async fn from_request_parts(parts: &mut Parts, _state: &AppState) -> Result<Self, Self::Rejection> {
        parts.extensions.get::<AuthUser>()
            .map(|user| Self { user_id: user.user_id })
            .ok_or_else(|| {
                tracing::error!(uri = %parts.uri, "请求缺少认证中间件注入的用户身份");
                AppError::Internal("认证上下文缺失")
            })
    }
}
```

两个设计决定：

**只存 `user_id`。** 不存用户名、邮箱等资料——那些需要时才查库，避免中间件为了填充扩展多做一次查询。

**缺失时"失败关闭"。** 如果路由没经过认证中间件，`CurrentUser` 提取会返回 500，而不是当成匿名放行。注释说得很明确：否则一次路由改写就可能静默地把接口暴露出去。

```rust
// src/common/auth_extractor.rs:101  测试锁定这个行为
async fn fails_closed_without_authenticated_user() { /* 断言返回 Internal */ }
```

### `from_fn_with_state` 而不是 `from_fn`

```rust
// src/app/routes.rs:40
.route_layer(axum::middleware::from_fn_with_state(state, crate::common::auth::require_login));
```

原因是类型系统的细节（`src/app/routes.rs:29-32` 的注释解释了）：`nest` 之后内部 Router 的状态类型已被解析为具体类型，中间件无法再依赖外层的 `with_state` 注入；`from_fn` 要求自己解析 `State`，所以必须用 `from_fn_with_state` 把状态**绑定到中间件上**。

`require_login` 签名里 `State<AppState>` 在第一个参数，也是这个原因。

### 认证本体

```rust
// src/common/auth.rs:99
async fn authenticate(state: &AppState, headers: &HeaderMap) -> Result<AuthUser, AppError> {
    // ① 只从 Cookie 取令牌
    let token = cookie::access_token_from_headers(headers, &state.auth.cookie)
        .ok_or(AppError::Unauthorized("未登录或登录已过期"))?;

    // ② 验签 + 校验 claims
    let verified = AuthService::verify_access_token(&state.jwt, &token)?;

    // ③ 查吊销列表
    match state.redis.is_access_token_revoked(&verified.jti).await {
        Ok(true) => return Err(AppError::Unauthorized("认证令牌已失效，请重新登录")),
        Ok(false) => {}
        Err(error) => tracing::warn!(%error, "查询令牌吊销列表失败，按未吊销处理"),  // ④ 降级
    }

    Ok(AuthUser { user_id: verified.user_id })
}
```

第 ④ 步是本章最值得记住的降级决策：**Redis 挂了按"未吊销"放行**。理由写在注释里——吊销是"登出立即生效"的增强，不是令牌有效性的前提。反过来如果失败关闭，一次 Redis 抖动就会把所有在线用户踢下线，把缓存组件故障放大成全站登录故障。

对比一下：如果这里是"防重放锁"而不是"吊销列表"，失败关闭才是对的。**降级方向取决于这个检查保护的是什么**——这就是为什么降级策略不能写在适配层，必须写在 Service/中间件里。

## 8.4 动手练习：写一个 `X-Request-Id` 中间件

这是最能检验"你是否真的理解中间件"的练习。目标：每个请求生成一个 request id，写进响应头，并让它出现在该请求的所有日志里。

```rust
// 建议写在 src/app/middleware.rs，然后在 create_app 里 .layer(...) 挂上
use axum::{extract::Request, middleware::Next, response::Response};

pub async fn request_id_middleware(mut request: Request, next: Next) -> Response {
    // 客户端传了就复用，没传就生成
    let request_id = request
        .headers()
        .get("x-request-id")
        .and_then(|value| value.to_str().ok())
        .map(str::to_owned)
        .unwrap_or_else(|| uuid::Uuid::now_v7().to_string());

    // ① 塞进请求扩展：Handler 里可以用 Extension<String> 取到
    request.extensions_mut().insert(request_id.clone());

    // ② 调用下游
    let mut response = next.run(request).await;

    // ③ 回写响应头
    if let Ok(value) = axum::http::HeaderValue::from_str(&request_id) {
        response.headers_mut().insert("x-request-id", value);
    }

    response
}
```

进阶任务：

1. 用 `tracing::info_span!("request", request_id = %request_id)` 包住 `next.run`，让该请求内所有日志都带上这个 id（提示：需要 `tracing::Instrument` 的 `.instrument(span)`）。
2. 思考：这个中间件应该挂在 `logging_middleware` 的**外层还是内层**？如果挂在内层，日志的 span 里能看到 request_id 吗？
3. 安全考虑：如果客户端随便传一个超长或含注入字符的 `x-request-id`，会有什么风险？加个长度和字符集限制。
