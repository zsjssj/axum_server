# 02 项目全景与启动流程

**本章目标**：看懂一个 Rust 后端从 `cargo run` 到"能接流量"之间发生了什么，并理解每一步**失败时该不该让进程退出**。这是一个新手最容易忽略、但线上最要命的设计点。

---

## 2.1 先看全局：这个项目在做什么

一个 HTTP API 服务，当前有两个业务模块：

- **用户模块**：用户的增删改查（`/api/v1/users`）
- **认证模块**：登录、刷新令牌、登出、当前用户（`/api/v1/auth/*`）

技术栈（`Cargo.toml`）：

| 依赖 | 角色 | 一句话说明 |
| --- | --- | --- |
| `axum` 0.7 | Web 框架 | 路由、提取器、响应 |
| `tokio` | 异步运行时 | 执行 `async` 任务、阻塞任务线程池 |
| `sqlx` 0.8 | 数据库客户端 | 连接池、迁移、参数绑定、行映射 |
| `redis` + `bb8` | 缓存/临时状态 | 限流、令牌吊销、用户缓存 |
| `serde` | 序列化 | JSON 与配置 |
| `validator` | 校验 | 声明式字段规则 |
| `config` + `dotenvy` | 配置 | 分层覆盖 |
| `tracing` / `tracing-subscriber` | 日志 | 结构化日志 |
| `argon2` | 密码哈希 | 慢哈希，抗离线爆破 |
| `jsonwebtoken` | JWT | HS256 签发与校验 |
| `utoipa` / `utoipa-swagger-ui` | 文档 | 从注解生成 OpenAPI |

依赖的版本和 `features` 不是随手写的，几个容易踩的点：

```toml
# Cargo.toml:19  redis 的关键 feature
redis = { version = "1.7.1", default-features = false, features = [
    "tokio-comp",       # 异步连接
    "bb8",              # 连接池集成
    "script",           # EVAL：限流需要 Lua 脚本原子执行
    "tokio-rustls-comp",# 让 rediss:// 真的能用（TLS）
] }
```

```toml
# Cargo.toml:28  sqlx 没有开 macros 特性
sqlx = { version = "0.8", features = ["runtime-tokio-rustls", "postgres", "chrono", "uuid"] }
```

没开 `macros` 意味着不能用 `sqlx::query!` 那种**编译期查库校验**的写法，只能用手写 SQL + `query_as` 运行时映射。这是一个取舍：`query!` 更安全但要求编译时有可连的数据库（CI 里很麻烦），本项目选了"编译零依赖数据库"。

## 2.2 分层：谁可以调用谁

```text
                ┌──────────────────────────────┐
HTTP 请求 ───→  │ Router / Middleware          │  app/routes.rs, common/auth.rs
                └──────────────┬───────────────┘
                               ▼
                ┌──────────────────────────────┐
                │ Handler                      │  modules/*/handler.rs
                │ 只做 HTTP 适配：提取、调用、包装 │
                └──────────────┬───────────────┘
                               ▼
                ┌──────────────────────────────┐        ┌───────────────────┐
                │ Service                      │ ─────→ │ infrastructure    │
                │ 业务规则、顺序、错误归类        │        │ Redis 适配层        │
                └──────────────┬───────────────┘        └───────────────────┘
                               ▼
                ┌──────────────────────────────┐
                │ Repository                   │  modules/*/repository.rs
                │ 只写 SQL，返回实体或 Option    │
                └──────────────┬───────────────┘
                               ▼
                        PostgreSQL
```

规则只有一条：**上层可以调用下层，下层不能反向依赖上层。** 具体的"不该做什么"：

| 层 | 不该做 |
| --- | --- |
| Handler | 写 SQL、承载复杂业务规则、直接决定 409 还是 500 |
| Service | 碰 `StatusCode`、`Json`、`IntoResponse` |
| Repository | 决定 HTTP 状态码、决定业务流程、调用 Service |
| infrastructure | 决定"Redis 挂了要不要回退数据库" |

最后一条特别值得注意：`infrastructure/redis.rs` 只**如实返回错误**，降级决策在 Service。因为"能不能降级"是业务语义问题——缓存挂了可以回退数据库，令牌吊销挂了也可以放行，但如果将来加一个"防重复提交"的 Redis 锁，那就不能随便放行。适配层替调用方做决定，会让行为变得不可推断。

## 2.3 启动流程精读

`src/main.rs` 一共 59 行，是整个服务的骨架。

```rust
// src/main.rs:15
#[tokio::main(worker_threads = 4)]
async fn main() {
    if let Err(error) = run().await {
        eprintln!("server error: {error}");
        std::process::exit(1);      // 非零退出码 = 部署系统能识别启动失败
    }
}
```

把真正的逻辑放在 `run()` 里，是为了能用 `?` 在任意一步返回错误，而 `main` 只负责"打日志 + 非零退出"。这比在每个 `await` 后面手写 `if let Err` 干净得多。

`run()` 的 9 个步骤（对应 `src/main.rs:23-54`）：

| 步骤 | 代码位置 | 做什么 | 失败时 |
| --- | --- | --- | --- |
| 1 | `:24` | `AppConfig::new()` 读取四级配置 | **退出**：没配置就没有正确行为可言 |
| 2 | `:27` | `config.validate()` 校验配置 | **退出**：弱 JWT 密钥等问题必须在监听前暴露 |
| 3 | `:28` | `init_tracing` 初始化日志 | 不失败（非法级别回落 `info`） |
| 4 | `:30` | 创建 PostgreSQL 连接池 | **退出**：数据库是权威依赖 |
| 5 | `:31` | 执行迁移 | **退出**：结构不完整不能接流量 |
| 6 | `:34` | 按配置创建引导账号 | **退出**：否则部署完没人能登录 |
| 7 | `:41` | 创建 Redis 访问器 | **退出**：地址非法说明配置写错了 |
| 8 | `:43` | `PING` 探测 Redis | **只告警**：各项功能都能降级 |
| 9 | `:46-52` | 组装 App → 绑定端口 → 开始 serve | **退出**：端口占用等 |

### 为什么第 7 步和第 8 步的失败策略不一样

这是整个启动流程里最值得学的设计：

```rust
// src/main.rs:41
let redis_store = RedisStore::from_config(&config.redis)
    .map_err(|error| format!("Redis 初始化失败: {error}"))?;   // 地址非法 → 退出
if let Err(error) = redis_store.ping().await {
    tracing::warn!(%error, "Redis 不可用，登录限流、令牌吊销与用户缓存将降级运行");  // 连不上 → 只告警
}
```

- **构造失败 = 配置错误**。`redis://` 写错、URL 非法，属于"人写错了"，重试一万次也不会好，继续跑只会让所有 Redis 功能静默失效，排障时根本想不到是配置写错。
- **连接失败 = 依赖暂时不可用**。可能是 Redis 正在重启、网络抖动。此时服务仍有完整的降级路径（见[第 10 章](./10-Redis与降级设计.md)），直接退出反而放大了故障面。
- **真正兜底的是 `/ready`**：Redis 不可用时它返回 `503`，编排系统据此把实例移出流量池。**"能启动"和"该接流量"是两件事**，本项目用两个接口把它们分开。

### 为什么迁移必须在开始监听之前

```rust
// src/main.rs:31
database::run_migrations(&db_pool).await?;
```

如果先监听再迁移，中间会有一个窗口：服务能接请求，但表还不存在——每个请求都 500。而且多实例滚动发布时，新旧代码可能对应不同表结构，这个窗口越长越危险。

迁移是**编译期嵌入**的：

```rust
// src/infrastructure/database.rs:19
pub async fn run_migrations(pool: &PgPool) -> Result<(), MigrateError> {
    sqlx::migrate!("./migrations").run(pool).await?;
    tracing::info!("database migrations completed");
    Ok(())
}
```

`sqlx::migrate!` 是个宏，把 `migrations/` 目录**编译进二进制**。好处是部署产物自带迁移，不依赖运行目录里有没有 SQL 文件；代价是改了迁移文件必须重新编译。

> **重要约定**：已经执行过的迁移文件**不能改**，只能新增。SQLx 记录了每个文件的校验和，改历史文件会让下次启动直接报错退出。详见[第 04 章](./04-数据库与SQLx.md)。

### 为什么引导账号夹在迁移和 Redis 之间

```rust
// src/main.rs:34
bootstrap::ensure_bootstrap_user(&db_pool, &config.bootstrap)
    .await
    .map_err(|error| format!("引导账号初始化失败: {error:?}"))?;
```

位置有两个约束：

- **在迁移之后**：得先有 `users` 表才能插数据。
- **在监听之前**：`/api/v1` 下全部接口默认要登录，而"创建用户"接口自己也在里面。空库时"要登录得先有用户，要建用户得先登录"，这个死锁必须在开始接流量之前解开，否则服务虽然"启动成功"，却每个业务接口都 401。

它不会变成长期后门，因为有三个约束共同兜着（`src/app/bootstrap.rs:29-40`）：

1. 开关默认 `false`，必须显式打开；
2. 只在 `users` 表**为空**时执行（判据是表空，不是"该用户名不存在"），已有用户的库永远不会被写入；
3. 字段校验复用 `CreateUserRequest`、哈希复用 `common::password`，不另开一套弱规则。

### 为什么用 `into_make_service_with_connect_info`

```rust
// src/main.rs:52
axum::serve(listener, app.into_make_service_with_connect_info::<std::net::SocketAddr>()).await?;
```

普通的 `app.into_make_service()` 拿不到客户端 IP。而登录和刷新接口需要记录 `client_ip` 做安全审计，所以要用带连接信息的版本，Handler 里就能通过 `ConnectInfo<SocketAddr>` 提取到对端地址：

```rust
// src/modules/auth/handler.rs:170
connect_info: Option<ConnectInfo<SocketAddr>>,
```

注意它是 `Option`：单元测试里用 `oneshot` 直接调 Router 时没有真实连接，写成必选会在测试里 panic。

## 2.4 应用装配：`create_app`

```rust
// src/app/mod.rs:22
pub fn create_app(db_pool: PgPool, redis: RedisStore, config: &AppConfig) -> Router {
    let state = AppState::new(db_pool, redis, config.jwt.clone(), config.auth.clone());

    Router::new()
        .merge(routes::health_routes())              // /, /health, /ready（匿名）
        .merge(routes::api_routes(state.clone()))    // /api/v1/**（默认要登录）
        .merge(openapi::routes())                    // /swagger-ui, /api-docs
        .fallback(routes::not_found_handler)         // 404 也走统一信封
        .method_not_allowed_fallback(routes::method_not_allowed_handler)  // 405 同理
        .layer(cors_layer())
        .layer(logging_middleware())
        .with_state(state)
}
```

几个值得注意的决定：

**函数签名收 `&AppConfig` 而不是拆散的字段。** 注释写得很清楚：后续新增需要共享的配置时，不用改函数签名和所有调用点。

**Redis 由调用方创建后传入，不在这里构造。** 因为构造可能失败，把失败点留在启动流程里才能给出"哪个组件初始化失败"的明确错误，而不是在 `create_app` 里 panic。

**两个 fallback 都是自定义函数。** Axum 默认的 404/405 是纯文本响应，会绕过项目的 `ApiResponse` 信封，客户端需要两套解析逻辑。这个细节在第 07 章展开。

**`with_state` 放在最后。** `Router<S>` 的类型参数表示"还缺哪种状态"；`with_state(state)` 把它填成 `Router<()>`，才是能交给 `serve` 的完整 Router。

## 2.5 一个请求进来之后

先建立整体印象，具体细节在第 05、08 章：

```text
TCP 连接
  ↓
/health、/ready        → 匿名，直接进 Handler
/swagger-ui            → 匿名，静态资源
/api/v1/**             → 先过认证中间件（白名单除外）→ Handler
其他路径                → not_found_handler → 404 统一信封
已匹配路径但方法不对     → method_not_allowed_handler → 405 统一信封
```

## 2.6 动手练习

1. **观察失败策略**：把 `config/default.toml` 的 `jwt.secret` 改短（少于 32 字符）后启动，记录报错；再改回去。然后在 `redis.url` 写成 `http://...` 启动，对比两次错误信息的清晰度。
2. **验证 Redis 降级**：停掉 Redis（`docker stop`），启动服务。观察 `/health` 返回 200、`/ready` 返回 503，但登录和查询用户仍然可用。
3. **看迁移表**：连上数据库执行 `SELECT version, description, success FROM _sqlx_migrations;`，确认每个迁移文件的版本、描述与校验和都被记录。
4. **加一条启动日志**：在 `run()` 里监听成功之后加一行 `tracing::info!`，打印当前 `RUN_MODE` 和 `key_prefix`。改完启动一次确认能看到。
5. **故意让端口被占**：再跑一个 `cargo run`，观察第二个进程如何失败、退出码是多少（`echo $LASTEXITCODE` / `echo $?`）。
