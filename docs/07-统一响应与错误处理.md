# 07 统一响应与错误处理

**本章目标**：看懂"所有接口返回同一个形状"是怎么做到的，以及错误为什么要在**一个地方**收口。这是后端工程化程度最直观的体现——也是新手项目和大厂代码差距最明显的地方。

---

## 7.1 问题：不统一会怎样

假设三个接口各有各的错误格式：

```json
{ "error": "用户名已存在" }                                  // 接口 A
{ "message": "用户名已存在", "success": false }               // 接口 B
{ "code": 409, "msg": "用户名已存在", "data": null }          // 接口 C
```

前端的处境：

```javascript
// 每个接口都要写一个 if-else 分支来解析错误
const data = await res.json();
if (data.error) { ... } else if (data.success === false) { ... } else if (data.code !== 0) { ... }
```

加一个接口就加一条分支。所以成熟项目的第一条工程约定就是：**统一信封**。

## 7.2 响应信封

```rust
// src/common/response.rs:6
pub struct ApiResponse<T> {
    pub code: i32,          // 业务码
    pub message: String,    // 人读的提示
    pub data: Option<T>,    // 业务数据
}
```

成功：

```json
{
  "code": 0,
  "message": "查询成功",
  "data": { "public_id": "0199...", "username": "testuser" }
}
```

失败（带字段明细）：

```json
{
  "code": 40001,
  "message": "请求参数校验失败",
  "data": { "details": [ { "field": "email", "message": "邮箱格式不正确" } ] }
}
```

失败（无附加信息）：`data` 为 `null`。

构造器有两个层次：

```rust
// src/common/response.rs:17
impl<T> ApiResponse<T> {
    pub fn success(message: impl Into<String>, data: T) -> Self { /* code: 0 */ }
    pub fn error(code: ApiCode, message: impl Into<String>, data: Option<T>) -> Self { /* ... */ }
}

// src/common/response.rs:35  专门给"没有数据"的成功响应用
impl ApiResponse<()> {
    pub fn success_without_data(message: impl Into<String>) -> Self { /* data: None */ }
}
```

为什么要单独一个 `impl ApiResponse<()>`？因为泛型 `T` 必须被推断出来。删除用户接口返回"没有数据"，写 `ApiResponse::success("删除成功", ())` 也能过，但 `data` 会变成 `null` 的语义不明确（是"空对象"还是"没有"）。单独提供 `success_without_data` 让调用点自解释：

```rust
// src/modules/user/handler.rs:168
Ok(Json(ApiResponse::<()>::success_without_data("用户删除成功")))
```

## 7.3 两层状态：HTTP 状态码 + 业务码

```rust
// src/common/response.rs:48
#[derive(Debug, Clone, Copy)]
#[repr(i32)]
pub enum ApiCode {
    Success = 0,
    BadRequest = 40000,
    ValidationError = 40001,
    UnsupportedMediaType = 40002,
    Unauthorized = 40100,
    NotFound = 40400,
    MethodNotAllowed = 40500,
    Conflict = 40900,
    TooManyRequests = 42900,
    InternalError = 50000,
    ServiceUnavailable = 50300,
}
```

两者职责不同：

| | HTTP 状态码 | 业务码 (code) |
| --- | --- | --- |
| 给谁看 | 网关、负载均衡、监控、通用 HTTP 客户端 | 前端业务代码 |
| 作用 | 协议层结果：成功 / 客户端错误 / 服务端错误 | 细分原因：是参数校验还是媒体类型？是限流还是未认证？ |
| 示例 | `422` | `40001` |

为什么要两份？因为 HTTP 状态码不够细：`400` 可以是"JSON 语法错"也可以是"字段校验失败"，前端想区分就得解析 message 字符串——而 message 是会变的。

编码规则也有讲究：`40 001` 中前三位是状态码、后两位是细分序号。新增错误时在对应号段里加，前端可以按号段做粗分类。

### `#[repr(i32)]` 和 `Success = 0`

```rust
// src/common/response.rs:49
#[repr(i32)]
pub enum ApiCode { Success = 0, /* ... */ }
```

两个细节：

**`#[repr(i32)]`**：让每个变体有明确的内存表示，可以用 `ApiCode as i32` 转换（`src/common/response.rs:67` 的 `From<ApiCode> for i32`）。没有它，Rust 不保证枚举的整数值。

**`Success = 0` 而不是复用 `200`**：如果用 `200`，会出现"HTTP 200 但业务码 200 表示成功、HTTP 400 但业务码 200 又是什么"的混乱。`0` 在业务码空间里没有歧义，且和 Unix 退出码的惯例一致（0 = 成功）。

> 注释里写得很直白：`Success` 必须显式声明为 `0`，否则会出现"HTTP 成功但业务码表示失败"的矛盾。这类"看起来只是数字选择"的问题，实际上是接口契约的一部分。

## 7.4 `AppError`：12 个变体收口所有错误

```rust
// src/common/error.rs:38
#[derive(Debug, Error)]
pub enum AppError {
    #[error("请求参数校验失败")]
    Validation(#[from] ValidationErrors),   // 字段级校验失败
    #[error("{0}")]
    BadRequest(&'static str),               // 请求格式不合法
    #[error("{0}")]
    UnprocessableEntity(&'static str),      // 语义不可处理
    #[error("{0}")]
    UnsupportedMediaType(&'static str),     // Content-Type 错
    #[error("{0}")]
    NotFound(&'static str),                 // 资源不存在
    #[error("请求方法不被允许")]
    MethodNotAllowed,                       // 方法不允许
    #[error("{0}")]
    Unauthorized(&'static str),             // 未认证
    #[error("{0}")]
    TooManyRequests(&'static str),          // 限流
    #[error("{0}")]
    ServiceUnavailable(&'static str),       // 依赖不可用
    #[error("{0}")]
    Conflict(&'static str),                 // 业务冲突
    #[error("数据库操作失败")]
    Database(#[from] sqlx::Error),          // 数据库错误（带原始错误）
    #[error("{0}")]
    Internal(&'static str),                 // 内部意外
}
```

设计上有两个刻意之处：

**提示语用 `&'static str`**。这意味着错误提示只能是编译期常量，不能在运行时 `format!` 拼接。好处是杜绝了"不小心把 SQL、连接串、用户输入拼进错误消息"的泄露路径。代价是同一变体不能带动态细节——需要动态信息时应该进日志，不是进响应。

**只有两个变体带数据**：`Validation(ValidationErrors)`（要输出字段明细）和 `Database(sqlx::Error)`（要把详细原因写进日志）。

### 为什么 `Display` / `source` 交给 `thiserror`

手写 `impl Display` + `impl Error` 时，有三处需要各自维护：

```rust
impl std::fmt::Display for RedisStoreError {                 // ① 每个变体的文案
    fn fmt(&self, f: &mut std::fmt::Formatter<'_>) -> std::fmt::Result {
        match self { /* ... */ }
    }
}

impl std::error::Error for RedisStoreError {
    fn source(&self) -> Option<&(dyn std::error::Error + 'static)> {   // ② 哪些变体有底层原因
        match self {
            Self::Command(error) => Some(error),
            Self::Serde(error) => Some(error),
            Self::Config(_) | Self::Connection(_) => None,
        }
    }
}

impl From<sqlx::Error> for AppError { /* ③ 转换 */ }
```

② 最容易漂：它不在变体定义旁边，新增一个包装型变体时编译器**不会**提醒你补 `Some(...)`——只要写个 `_ => None`，漏写就静默通过，`source` 链在排障时才发现是断的。`thiserror` 把这三件事变成变体上的属性：

```rust
#[derive(Debug, Error)]
pub enum RedisStoreError {
    #[error("Redis 配置不合法：{0}")]
    Config(String),                       // 没有底层原因，也不必额外写 None

    #[error("Redis 命令执行失败：{0}")]
    Command(#[from] RedisError),          // Display + source + From<RedisError>
    // ... 其余变体同理
}
```

收益是**「哪些变体有底层原因」与变体定义写在同一处**，读枚举就能回答，不依赖另一个 `match` 是否跟上；`#[from]` 还顺带给出 `From`，所以 `?` 的用法与原来的手写 `impl From` 完全一致。

**但 `Display` 不等于响应文案。** 对外说什么仍由 `IntoResponse` 里的常量决定，`Display` 只服务日志与启动期报错。因此 `Database` 的 `Display` 刻意只写"数据库操作失败"，原始原因留在 `source` 链里——即使将来有人误把 `Display` 拼进响应，也带不出 SQL 和表名。测试 `keeps_database_cause_out_of_display` 锁住了这条边界。

### 启动期为什么用 `anyhow`，而且只允许在启动期

`thiserror` 和 `anyhow` 不是二选一，它们解决的是两个不同位置的问题：

- **运行期**：错误要变成一个 HTTP 响应，所以必须**有类型**——`AppError` 的变体决定状态码和业务码，`thiserror` 负责把 `Display` / `source` / `From` 挂在变体上。
- **启动期**：错误要变成**一行排障日志**，然后让进程退出。没有请求、没有响应，也就不需要状态码；需要的是一层层能读懂的「哪一步失败了」。

```rust
// src/main.rs:36  启动期的典型写法
async fn run() -> anyhow::Result<()> {
    let config = AppConfig::new().context("加载应用配置失败")?;
    config.validate().context("应用配置校验失败")?;
    // ...
    let redis_store = RedisStore::from_config(&config.redis).context("Redis 初始化失败")?;
    // ...
}
```

改造前这里返回 `Box<dyn std::error::Error>`，并且为了让错误带上步骤名，只能写 `.map_err(|e| format!("引导账号初始化失败: {e:?}"))?`——`String` 不是 `error source`，**错误链在这一步就断了**，`Debug` 格式化也只是在补一个本来就不该丢的东西。现在每一步用 `.context()` 加一层说明，`main` 用 `{error:?}` 打印整条链：

```text
server error: 引导账号初始化失败

Caused by:
    0: duplicate key value violates unique constraint "users_username_key"
    1: ...
```

`main` 里必须写 `{error:?}` 而不是 `{error}`：`Display` 只给出最外层那一句，`Debug` 才会展开 `Caused by`。

**边界（这条比用法更值得记）：`anyhow` 只允许出现在 `main.rs`。** 两个具体的禁区：

| 禁区 | 会坏在哪里 |
| --- | --- |
| 给 `AppError` 加 `#[from] anyhow::Error` | 所有底层错误被压平成 `Internal` 500，`400/401/409` 的映射失效；`IntoResponse` 里"新增变体必须显式决定响应"的编译期保护也被绕过 |
| Service / Repository 返回 `anyhow::Result` | 调用方无法区分"可预期的业务错误"和"缺陷"，`&'static str` 那套泄露防护失去意义 |

一句话：**库和业务层给类型，二进制入口负责把它们串成一条可读的失败原因链。** 这也是 Rust 生态里最常见的分工方式（`thiserror` 写库、`anyhow` 写应用）。

### 完整映射表

| 变体 | HTTP | 业务码 | 对外 message |
| --- | ---: | ---: | --- |
| `Validation` | 422 | 40001 | `请求参数校验失败` + 字段明细 |
| `BadRequest` | 400 | 40000 | 自定义 |
| `UnprocessableEntity` | 422 | 40001 | 自定义 |
| `UnsupportedMediaType` | 415 | 40002 | 自定义 |
| `NotFound` | 404 | 40400 | 自定义 |
| `MethodNotAllowed` | 405 | 40500 | `请求方法不被允许` |
| `Unauthorized` | 401 | 40100 | 自定义 |
| `TooManyRequests` | 429 | 42900 | 自定义 |
| `ServiceUnavailable` | 503 | 50300 | 自定义 |
| `Conflict` | 409 | 40900 | 自定义 |
| `Database` | 500 | 50000 | **`服务器内部错误`**（固定） |
| `Internal` | 500 | 50000 | **`服务器内部错误`**（固定） |

注意最后两行：无论内部错误多具体，对外都是同一句话。**这是安全要求，不是偷懒。**

## 7.5 `IntoResponse`：错误到响应的唯一出口

```rust
// src/common/error.rs:83
impl IntoResponse for AppError {
    fn into_response(self) -> Response {
        let (status, code, message, details) = match self {
            Self::Validation(errors) => (
                StatusCode::UNPROCESSABLE_ENTITY,
                ApiCode::ValidationError,
                "请求参数校验失败",
                validation_details(&errors),
            ),
            Self::BadRequest(message) => (StatusCode::BAD_REQUEST, ApiCode::BadRequest, message, Vec::new()),
            // ... 其余变体
            Self::Database(error) => {
                tracing::error!(%error, "数据库操作失败");        // ← 细节进日志
                (StatusCode::INTERNAL_SERVER_ERROR, ApiCode::InternalError, "服务器内部错误", Vec::new())
            }
            Self::Internal(message) => {
                tracing::error!(%message, "内部操作失败");
                (StatusCode::INTERNAL_SERVER_ERROR, ApiCode::InternalError, "服务器内部错误", Vec::new())
            }
        };

        (status, Json(ApiResponse::error(code, message, (!details.is_empty()).then_some(ErrorData { details })))).into_response()
    }
}
```

三个要点：

**1. 一个 `match` 覆盖所有变体。** 如果将来给 `AppError` 加一个变体，这里会编译失败——**编译器强制你决定新错误该返回什么**。这比"忘了处理导致落到默认分支"安全得多。

**2. 只有 `Database` 和 `Internal` 打 error 日志。** 4xx 是客户端问题，不该污染 error 级日志（否则一次恶意扫描就能把日志刷满）。5xx 才需要告警。这是一个很容易被忽略的日志分级细节，见[第 11 章](./11-可观测性与健康检查.md)。

**3. `(!details.is_empty()).then_some(...)`**：没有字段明细时 `data` 为 `null`，而不是空数组 `[]`。这让前端可以用一个简单的 `if (data)` 判断。

## 7.6 校验明细：把 `validator` 的输出变成稳定结构

```rust
// src/common/error.rs:175
fn validation_details(errors: &ValidationErrors) -> Vec<ErrorDetail> {
    let mut details = errors.field_errors().iter()
        .flat_map(|(field, errors)| {
            errors.iter().map(move |error| ErrorDetail {
                field: if field == "__all__" { "_request".to_owned() } else { field.to_string() },
                message: error.message.as_deref().unwrap_or("字段值不合法").to_owned(),
            })
        })
        .collect::<Vec<_>>();

    details.sort_by(|left, right| left.field.cmp(&right.field));   // 按字段名排序
    details
}
```

三个处理：

| 处理 | 原因 |
| --- | --- |
| `__all__` → `_request` | `validator` 用 `__all__` 表示"整体校验失败"（如"至少提供一个字段"），直接暴露给前端很难理解 |
| `unwrap_or("字段值不合法")` | 规则没写 `message` 时有兜底，不会输出空字符串 |
| **排序** | `HashMap` 迭代顺序随机，不排序的话同一个错误请求可能返回不同顺序的数组，客户端缓存/测试断言都会飘 |

第三条是最容易被忽略的"稳定性"细节：**同一个输入，响应应该字节级可预测。**

## 7.7 404 / 405 也要走信封

Axum 默认的 404 是纯文本（"Not Found"），405 也是。这会让客户端需要两套解析逻辑。解法：

```rust
// src/app/mod.rs:29
.fallback(routes::not_found_handler)
.method_not_allowed_fallback(routes::method_not_allowed_handler)
```

```rust
// src/app/routes.rs:166
pub(crate) async fn not_found_handler() -> AppError {
    AppError::NotFound("接口不存在")
}

pub(crate) async fn method_not_allowed_handler() -> AppError {
    AppError::MethodNotAllowed
}
```

返回 `AppError` 就够了——`AppError` 实现了 `IntoResponse`，所以 Axum 会自动把它变成统一的 JSON 响应。这两个函数**没有一行 JSON 代码**，这就是"收口到一个类型"的收益。

## 7.8 错误响应的信息边界

| 内容 | 能不能对外 |
| --- | --- |
| 用户名已存在 | ✅ 这是业务语义，用户需要知道 |
| `duplicate key value violates unique constraint "users_username_key"` | ❌ 泄露表名和约束名 |
| 密码错误 / 用户不存在（统一文案） | ✅ 但必须**合并成同一句**，否则形成用户名枚举通道 |
| SQL 语句、连接串、堆栈 | ❌ 只进日志 |
| 相邻服务的错误原文 | ❌ 可能包含内网地址 |

本项目用 `&'static str` + 固定文案从类型层面约束了这一点。第 09 章会讲另一个相关设计：密码错误的文案为什么要和"用户不存在"完全一致。

## 7.9 测试如何锁定这些契约

响应信封这类"约定"，最怕被人无意识改坏。项目用测试锁住：


## 7.10 动手练习

1. **加一个错误变体**：给 `AppError` 加 `PayloadTooLarge(&'static str)`（413 / 业务码 `41300`），在 `ApiCode` 里加对应项，然后 `cargo build`。观察编译器在 `IntoResponse` 的 `match` 里报"未覆盖所有模式"——这就是"新增错误必须显式决定响应"的强制性。
2. **验证排序稳定性**：把 `validation_details` 的 `sort_by` 注释掉，跑 `cargo test` 里的 `returns_field_details_for_invalid_json_request` 多次（`for` 循环跑 100 次），看断言是否会飘。
3. **观察日志分级**：请求一个不存在的路径（404），确认日志里**没有** error 级记录；再把 `readiness_handler` 的数据库检查指向一个错误端口，触发 503，确认有 warn/error 记录。
4. **理解 `&'static str` 的代价**：尝试在 `AppError::NotFound` 里传一个 `format!("用户 {id} 不存在")`，看编译器怎么拒绝你。然后想清楚：如果确实需要动态信息，应该走哪条路？
