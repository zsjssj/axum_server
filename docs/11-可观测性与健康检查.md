# 11 可观测性与健康检查

**本章目标**：让服务"出问题时能自己说清楚发生了什么"。可观测性不是加日志，而是**在正确的位置、以正确的级别、带上正确的字段**记录信息，并用健康检查让编排系统能正确决策。

---

## 11.1 为什么用 `tracing` 而不是 `println!`

| 方案 | 问题 |
| --- | --- |
| `println!` | 无级别、无结构、无法按模块过滤；并发时输出交错 |
| `log` + 简单格式 | 有级别，但只有字符串，无法结构化查询 |
| **`tracing`** | 有级别 + **结构化字段** + **span（带上下文的时间区间）** |

结构化字段的价值在排障时最明显：

```rust
// 非结构化
println!("登录失败: {username} 失败 {count} 次");

// 结构化（本项目风格）
tracing::warn!(%username, recent_failures, "登录失败次数超过阈值，暂时拒绝登录");
```

后者能被日志系统按 `username`、`recent_failures` 建索引和聚合，比如"统计今天被限流最多的 10 个用户名"——非结构化文本只能靠正则硬抠。

## 11.2 初始化：一个函数，两行代码

```rust
// src/main.rs:75
fn init_tracing(level: &str) {
    let filter = EnvFilter::try_new(level).unwrap_or_else(|_| EnvFilter::new("info"));
    tracing_subscriber::fmt().with_env_filter(filter).init();
}
```

三个细节：

**① 过滤表达式来自配置。** `log.level` 的值直接当 `EnvFilter` 表达式用，所以可以写：

```toml
[log]
level = "info"                      # 全部 info
# level = "debug"                   # 全开（本地开发）
# level = "info,sqlx=warn"          # 全局 info，但库 SQL 日志只保留 warn
```

第二种写法在生产环境特别有用：`sqlx` 在 `debug` 级会打印每条 SQL 和参数，量大且可能包含敏感数据，压到 `warn` 就安静了。

**② 非法级别回落 `info`，不 panic。** 日志配置写错不该让服务起不来。

**③ 注意 `RUST_LOG` 环境变量不会生效。** `with_env_filter(filter)` 用的是配置值，而不是 `EnvFilter::from_default_env()`。如果你习惯了设 `RUST_LOG=debug` 调日志，在这个项目里要改 `APP__LOG__LEVEL=debug`。这是一个容易踩的坑，也是**一个可以改进的点**（见[第 14 章](./14-生产化与进阶.md)）。

## 11.3 请求日志：`TraceLayer`

```rust
// src/app/middleware.rs:46
pub fn logging_middleware() -> TraceLayer<SharedClassifier<ServerErrorsAsFailures>> {
    TraceLayer::new_for_http()
        .make_span_with(DefaultMakeSpan::new().level(Level::INFO))
        .on_response(DefaultOnResponse::new().level(Level::INFO).latency_unit(LatencyUnit::Millis))
}
```

它自动提供：

| 能力 | 说明 |
| --- | --- |
| 每个请求一个 span | 请求内的日志自动带上方法、路径等上下文 |
| 响应时记录状态码与耗时 | `latency_unit(Millis)` 统一成毫秒，便于做 SLO 统计 |
| 错误分类 | `ServerErrorsAsFailures`：5xx 记为 failure，4xx 不算服务端失败 |

最后一条值得展开：**4xx 不是服务端故障**。如果把 404、401 也当失败，一次扫描就能让"错误率"爆表，告警失去意义。

文件里保留的手写版本（`src/app/middleware.rs:26-45`，在 `ignore` 代码块里）说明这个 span 会带上请求信息。**中间件挂在最外层**（见[第 08 章](./08-全局状态与中间件.md)），所以被认证拒绝的 401 也会被记录。

## 11.4 日志级别的实际用法

级别不是"重要程度"，而是**"谁该被叫醒"**。

| 级别 | 什么时候用 | 本项目实例 |
| --- | --- | --- |
| `error!` | 需要人工介入：数据库挂了、内部不一致 | `common/error.rs:144` 数据库操作失败；`:153` 内部操作失败；`bootstrap.rs:52` 引导账号配置非法 |
| `warn!` | 降级或异常但服务仍可用 | `main.rs:58` Redis 不可用；`auth/service.rs:154` 计数回退数据库；`user/service.rs:79` 缓存读失败；`common/auth.rs:110` 吊销检查失败 |
| `info!` | 生命周期与关键业务节点 | `main.rs:67` server started；`database.rs:13` 池已连；`:22` 迁移完成；`bootstrap.rs:59` 已创建引导账号 |
| `debug!` | 排查时才有用，生产关掉 | `user/service.rs:75` 缓存命中；`auth/service.rs:459` 令牌校验失败原因 |

两个原则：

**① 4xx 不打 `error!`。** 只有 `Database` 和 `Internal` 打 error（`src/common/error.rs:143-162`）。否则恶意扫描能把日志刷满、把告警打爆，真正的故障反而被淹没。

**② 降级必须 `warn!`。** 降级不是"正常"，它意味着"功能不完整"。如果 Redis 挂了只字不提，运维永远不知道系统正在裸奔。

## 11.5 结构化字段：`%` 与 `?` 的区别

```rust
// 用 % ：调用 Display（给人看的字符串）
tracing::warn!(%error, "Redis 不可用，登录限流、令牌吊销与用户缓存将降级运行");

// 用 ? ：调用 Debug（给排查看的详细结构）
tracing::warn!(?error, "登出时吊销会话失败，仍继续清除客户端 Cookie");
```

| 记号 | 调用 | 输出形态 | 用在哪 |
| --- | --- | --- | --- |
| `%value` | `Display` | 紧凑可读 | 生产日志的主体信息 |
| `?value` | `Debug` | 完整结构、含类型细节 | 排查错误时需要更多信息 |
| `field = value` | 直接 | 结构化数值/字符串 | 计数、耗时、ID 等可聚合字段 |

看本项目的选择规律：`main.rs` 和 `common/auth.rs` 用 `%error`（给人看），`auth/handler.rs` 登出用 `?error`（要看细节），`error.rs` 用 `%error`（数据库错误 Display 已经足够具体）。

`tracing::warn!(%error, %username, "…")` 里的 `username` 是**字段**，不是格式参数——它会被单独提取，因此可以被日志后端索引。

## 11.6 `/health` 与 `/ready`：两件不同的事

```rust
// src/app/routes.rs:81
pub(crate) async fn health_handler() -> impl IntoResponse {
    Json(ApiResponse::success("请求成功", HealthResponse {
        status: "healthy",
        timestamp: chrono::Utc::now().to_rfc3339(),
    }))
}
```

```rust
// src/app/routes.rs:112
pub(crate) async fn readiness_handler(State(state): State<AppState>) -> Result<impl IntoResponse, AppError> {
    match sqlx::query("SELECT 1").execute(&state.db).await {
        Ok(_) => {}
        Err(error) => {
            tracing::warn!(%error, "数据库就绪检查失败");
            return Err(AppError::ServiceUnavailable("数据库不可用"));
        }
    }

    if let Err(error) = state.redis.ping().await {
        tracing::warn!(%error, "Redis 就绪检查失败");
        return Err(AppError::ServiceUnavailable("Redis 不可用"));
    }

    Ok(Json(ApiResponse::success("请求成功", ReadinessResponse { status: "ready", ... })))
}
```

| | `/health`（liveness） | `/ready`（readiness） |
| --- | --- | --- |
| 回答的问题 | 进程还活着吗？ | 现在能正确服务请求吗？ |
| 检查什么 | 什么都不检查，能返回就说明进程没死 | 数据库 `SELECT 1` + Redis `PING` |
| 失败时编排系统该做什么 | **重启**容器 | **摘除流量**，不重启 |
| Redis 故障时 | 200 | **503** |

**为什么 Redis 挂了 `/ready` 也要 503？** 因为各功能虽然降级了，但这个实例**不能提供完整的登录保护**（限流回退变慢、登出不再立即生效）。让它继续接流量意味着部分用户会得到"看起来正常的、安全性降低的"服务。编排系统把它移出流量池，反而能让流量集中到健康的实例上。

这里有一个微妙的取舍要意识到：**如果你把 `/ready` 当 `/health` 用（失败就重启），Redis 抖动会导致全部实例被反复重启**，故障被放大。所以两个接口必须配到正确的探针上。

```yaml
# Kubernetes 的正确配法（示意）
livenessProbe:  { httpGet: { path: /health, port: 3000 } }
readinessProbe: { httpGet: { path: /ready,  port: 3000 } }
```

## 11.7 目前缺什么（以及为什么现在可以缺）

| 缺口 | 影响 | 补齐方向 |
| --- | --- | --- |
| 没有请求 ID | 一次请求的多行日志无法串起来 | 加 `X-Request-Id` 中间件（第 08 章练习） |
| 没有 metrics | 无法做 QPS、P99、错误率看板与告警 | 接入 `axum-prometheus` 或用 OpenTelemetry |
| 没有分布式追踪 | 跨服务调用链不可见 | `tracing-opentelemetry` |
| 日志只输出到 stdout | 依赖容器日志采集 | 生产通常已由平台采集，够用 |
| `RUST_LOG` 不生效 | 与常见习惯不一致 | 改成 `EnvFilter::from_default_env().add_directive(...)` |

这些都是**有意识的阶段性取舍**：单实例、无跨服务调用的阶段，加 tracing 传播和 metrics 的收益低于成本。判断标准是"出了问题我能不能在 10 分钟内定位"——现在靠结构化日志基本可以。

## 11.8 动手练习

1. **调日志级别**：用 `APP__LOG__LEVEL=debug` 启动，请求一次用户详情两次（让第二次命中缓存），观察 `用户详情命中缓存` 这条 debug 日志；再换成 `info` 确认它消失。
2. **观察 span**：请求一次接口，观察 `TraceLayer` 输出的 span 里带了哪些字段（method、uri、latency）。对比一下你把 span 级别改成 `DEBUG` 后的输出。
3. **验证 `/ready` 语义**：停掉 Redis → `/ready` 返回 503 且日志有 warn；`/health` 仍 200。再停掉 PostgreSQL（`docker stop`）→ 两个接口分别什么表现？
4. **加请求 ID**：完成第 08 章的练习，然后让 `TraceLayer` 的 span 也带上 `request_id`，验证一次请求的所有日志都能被 grep 出来。
5. **加一条指标日志**：在 `require_login` 的失败分支加一行 `tracing::warn!(reason = "no_token", uri = %request.uri().path(), "认证失败")`，然后按 `reason` 字段聚合统计。思考：为什么用字段比把原因拼进 message 好？
